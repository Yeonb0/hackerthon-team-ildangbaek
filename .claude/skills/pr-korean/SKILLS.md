# 한국어 Pull Request 생성

현재 브랜치의 실제 변경 범위를 근거로 한국어 PR 제목과 본문을 작성하고 GitHub에 Draft PR을 생성한다.

## 기본 규칙

- PR 제목과 본문을 한국어로 작성한다. 코드 식별자, 명령어, 파일명은 원문을 유지한다.
- 사용자가 대상 브랜치를 지정하지 않으면 원격 저장소의 기본 브랜치를 사용한다.
- 기본적으로 Draft PR을 생성한다. 사용자가 명시적으로 요청할 때만 Ready for review로 생성한다.
- `.github/PULL_REQUEST_TEMPLATE.md`가 있으면 구조를 유지하고 모든 항목을 실제 변경사항으로 채운다.
- 확인하지 않은 테스트를 통과한 것처럼 표시하지 않는다. 실행하지 못한 검증은 이유와 함께 명시한다.
- 관련 없는 사용자 변경을 자동으로 스테이징하거나 커밋하지 않는다.

## 워크플로

1. 게시 범위를 확인한다.
   - `git status -sb`로 현재 브랜치와 작업 트리 상태를 확인한다.
   - `gh auth status`와 GitHub 원격 저장소 접근 상태를 확인한다.
   - 원격 기본 브랜치와 merge-base를 확인한다.
   - `git log <base>..HEAD`, `git diff --stat <merge-base>...HEAD`, `git diff <merge-base>...HEAD`로 커밋된 전체 변경을 읽는다.
   - staged, unstaged, untracked 변경도 각각 확인한다.

2. 변경 범위를 결정한다.
   - 변경사항이 하나의 작업으로 명확히 묶이면 현재 작업 트리 변경도 포함한다.
   - 서로 무관한 변경이 섞여 있으면 파일을 임의로 포함하지 말고, 포함 범위를 묻는 질문 하나만 한다.
   - 기본 브랜치에서 작업 중이면 `agent/<description>` 형식의 브랜치를 만든다. 이미 기능 브랜치라면 현재 브랜치를 유지한다.

3. 커밋 전 검증을 수행한다.
   - 변경된 영역에 가장 가까운 테스트를 먼저 실행한다.
   - 저장소에서 지원하는 린트, 타입 검사 또는 빌드를 필요한 범위에서 실행한다.
   - 실패하면 원인을 확인하고 요청 범위 안에서 수정한 뒤 다시 검증한다.

4. 변경사항을 커밋하고 푸시한다.
   - 저장소의 커밋 규칙을 따르고, 별도 규칙이 없으면 Conventional Commit 형식을 사용한다.
   - 의도한 파일만 명시적으로 스테이징한다.
   - 현재 브랜치를 원격에 tracking 설정과 함께 푸시한다.

5. 한국어 PR 내용을 작성한다.
   - 제목은 전체 diff의 핵심 결과를 한 문장으로 요약한다.
   - 본문은 템플릿을 기준으로 변경 내용, 변경 이유, 영향 범위, 검증 결과를 구체적으로 작성한다.
   - 버그 수정이면 확인된 근본 원인을 포함한다.
   - 관련 이슈나 후속 작업이 없으면 해당 항목에 `없음`을 명시한다.

6. PR을 생성한다.
   - `gh pr list --head <head> --base <base> --state open`으로 기존 PR을 먼저 확인한다.
   - 기존 PR이 있으면 새 PR을 중복 생성하지 말고 URL과 현재 상태를 반환한다.
   - 본문을 임시 Markdown 파일에 저장한다.
   - 기본 명령은 `gh pr create --draft --title "<제목>" --body-file <파일> --base <base> --head <head>`를 사용한다.
   - 사용자가 Ready for review를 요청했을 때만 `--draft`를 제거한다.

7. 결과를 보고한다.
   - 브랜치, 커밋, PR 대상, PR URL, Draft 여부, 실행한 검증과 실패 또는 생략된 검증을 요약한다.

## 중단 조건

- GitHub 인증 또는 원격 저장소 접근 권한이 없으면 변경사항을 푸시하지 않고 필요한 인증 상태를 보고한다.
- 검증 실패가 해결되지 않으면 PR을 성공으로 보고하지 않는다.
- 변경 범위가 불명확하고 잘못된 파일을 게시할 위험이 있으면 범위를 확인할 때까지 스테이징, 커밋, 푸시를 중단한다.
