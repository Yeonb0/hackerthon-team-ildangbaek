## 2. 인증 및 계정

### F-AUTH-01. 로그인 `확정`

| 항목 | 내용 |
| --- | --- |
| 기능 ID | F-AUTH-01 |
| 기능명 | 로그인 |
| 설명 | 지원되는 로그인 수단으로 인증하여 계정과 누적 데이터를 불러온다. |
| 관련 화면 | S-00 |
| 우선순위 | H |
| Actor | 비로그인 사용자 |
| 선행 조건 | 앱 실행 및 네트워크 연결 |
| 트리거 | 로그인 화면에서 로그인 수단 선택 |
| 입력 | 로그인 제공자가 반환한 인증 정보 |
| 출력 | 서비스 인증 정보, 신규 여부, 온보딩 완료 여부 |
| 후행 조건 | 로그인 상태 생성 |
| DB 영향 | 최초 사용자 계정 생성 또는 기존 계정 조회 |
| API 필요 | O |

**Business Rule**

1. 동일한 인증 계정은 하나의 서비스 사용자 계정에 대응한다.
2. 기존 가입자는 기존 기록과 개인 성분 프로파일을 그대로 불러온다.
3. 로그인 응답에는 `isNewUser`, `onboardingCompleted` 두 값을 포함한다.
4. 신규 가입자는 S-01부터 온보딩을 진행한다.
5. 기존 가입자이면서 온보딩 완료 상태라면 홈(S-07 또는 S-08)으로 이동한다.
6. 기존 가입자이지만 온보딩 미완료라면 **마지막 미완료 단계부터** 재개한다.
7. 온보딩 완료 후에는 뒤로가기로 온보딩 스택에 되돌아갈 수 없도록 루트 스택을 교체한다.

**상세 동작**

```
로그인 수단 선택
  ↓
외부 인증 수행
  ↓
서버에서 사용자 조회 · 없으면 생성
  ↓
신규/기존 판별
  ↓
서비스 인증 상태 생성
  ↓
다음 화면 결정 (온보딩 / 홈)
```

**예외 처리**

| 상황 | 처리 |
| --- | --- |
| 인증 취소 | S-00 유지, 별도 오류 표시 없음 |
| 외부 인증 실패 | 로그인 실패 안내 |
| 네트워크 오류 | 재시도 제공 |
| 서버 오류 | 잠시 후 재시도 안내 |

**Acceptance Criteria**

- 인증 성공 시 올바른 사용자 계정으로 로그인된다.
- 기존 사용자의 기록이 초기화되지 않는다.
- 실패 시 비로그인 상태가 유지된다.

### F-AUTH-02. 자동 로그인 및 인증 상태 유지 `확정`

| 항목 | 내용 |
| --- | --- |
| 기능 ID | F-AUTH-02 |
| 기능명 | 자동 로그인 및 인증 상태 유지 |
| 설명 | 로그인한 사용자가 앱을 다시 실행했을 때 반복 인증 없이 이용하도록 한다. |
| 우선순위 | H |
| Actor | 로그인 이력이 있는 사용자 |
| 트리거 | 앱 실행 |
| 입력 | 저장된 인증 정보 |
| 출력 | 로그인 상태 |
| API 필요 | O |

**Business Rule**

1. 앱 실행 시 인증 상태를 우선 확인한다.
2. 유효한 인증 상태라면 S-00을 생략한다.
3. Access Token 만료 시 Refresh Token으로 자동 갱신한다.
4. 갱신 불가 시 S-00으로 이동한다.
5. 온보딩 미완료 사용자는 자동 로그인되더라도 홈이 아니라 미완료 온보딩 단계로 진입한다.

**Acceptance Criteria**

- 정상 로그인 상태에서 앱 재실행 시 로그인 화면이 반복 노출되지 않는다.
- 복구 불가능한 만료 상태에서는 보호 API 접근이 차단된다.

### F-AUTH-03. 로그아웃 `확정`

| 항목 | 내용 |
| --- | --- |
| 기능 ID | F-AUTH-03 |
| 기능명 | 로그아웃 |
| 설명 | 현재 로그인된 계정의 인증 상태를 종료한다. |
| 관련 화면 | S-23 (설정 메뉴 3행 중 로그아웃) |
| 우선순위 | M |
| 트리거 | 마이페이지 → 로그아웃 → 확인 |
| 후행 조건 | S-00 이동 |
| API 필요 | O |

**Business Rule**

1. 로그아웃 선택 즉시 처리하지 않고 확인 팝업을 제공한다.
2. 취소하면 S-23을 유지한다.
3. 확인하면 클라이언트 인증 정보를 제거하고 서버 Refresh Token을 폐기한다.
4. 서버에 저장된 기록 자체는 삭제하지 않는다.

**Acceptance Criteria**

- 로그아웃 후 인증이 필요한 화면에 접근할 수 없다.
- 동일 계정으로 다시 로그인하면 기존 기록이 복구된다.

### F-ONBOARD-01. 기본 정보 입력 `변경`

| 항목 | 내용 |
| --- | --- |
| 기능 ID | F-ONBOARD-01 |
| 기능명 | 기본 정보 입력 |
| 설명 | 이름 · 성별 · 나이를 한 화면에서 순차적으로 입력받는다. |
| 관련 화면 | S-01 |
| 우선순위 | H |
| Actor | 최초 가입 사용자 |
| 선행 조건 | F-AUTH-01 성공 |
| 입력 | 이름, 성별, 나이 |
| 출력 | 사용자 기본 프로필 |
| DB 영향 | 사용자 프로필 생성/수정 |
| API 필요 | O |

**Business Rule**

1. 초기 진입 시 **이름 필드만** 노출한다.
2. 이름이 입력되면 성별 필드가 나타난다.
3. 성별이 선택되면 나이 필드가 나타난다.
4. 세 필드가 모두 채워지기 전까지 `다음` 버튼은 비활성 상태를 유지한다.
5. 이름은 앱 내부 표시 이름으로만 사용한다.
6. 성별 선택지는 `여성 / 남성 / 선택 안 함` 단일 선택이다.
7. **성별 값은 S-04 진입 여부를 판별하는 데 사용하므로 반드시 저장한다.**
8. 나이는 스테퍼(− / +)로 입력하며 기본값은 설정해두지 않는다. 
9. 이미 입력한 필드를 되돌려 수정해도 하위 필드의 입력값은 유지한다.

**Validation**

| 필드 | 규칙 |
| --- | --- |
| 이름 | 필수 · 공백만 입력 불가 · 1~10자 |
| 성별 | 필수 · `FEMALE / MALE / UNSPECIFIED` |
| 나이 | 필수 · 1~100 정수  |

**예외 처리**

| 상황 | 처리 |
| --- | --- |
| 필수 입력 누락 | `다음` 비활성 유지 |
| 저장 실패 | 입력값 유지 + 재시도 제공 |

**Acceptance Criteria**

- 이름을 입력하기 전에는 성별·나이 필드가 화면에 없다.
- 세 값이 모두 유효할 때만 다음 단계로 이동한다.
- 저장 실패 시 입력했던 내용이 사라지지 않는다.

### F-ONBOARD-02. 피부 타입 선택 `신규`

| 항목 | 내용 |
| --- | --- |
| 기능 ID | F-ONBOARD-02 |
| 기능명 | 피부 타입 선택 |
| 설명 | 사용자가 인지하는 피부 타입을 중복 선택으로 입력받아 성분 반응 해석의 초기 기준으로 사용한다. |
| 관련 화면 | S-02 |
| 우선순위 | H |
| 선행 조건 | F-ONBOARD-01 완료 |
| 입력 | 피부 타입 (복수) |
| 출력 | 사용자 피부 타입 정보 |
| API 필요 | O |

**선택지**

| 값 | 라벨 | 판단 기준 설명 |
| --- | --- | --- |
| `OILY` | 지성 | 유분이 많고 쉽게 번들거려요 |
| `DRY` | 건성 | 당기고 각질이 잘 생겨요 |
| `SENSITIVE` | 민감성 | 쉽게 붉어지거나 따가워요 |
| `UNKNOWN` | 모르겠음 | 나머지 3개와 배타 |

**Business Rule**

1. 지성 · 건성 · 민감성은 중복 선택할 수 있다. 복합성을 표현하기 위함이다.
2. `모르겠음`을 선택하면 나머지 3개 선택이 즉시 해제되고 선택 불가 상태가 된다.
3. `모르겠음`이 선택된 상태에서 다른 항목을 선택하면 `모르겠음`이 해제된다.
4. 1개 이상 선택해야 `다음`이 활성화된다. `모르겠음`이 존재하므로 필수 선택 항목이다.
5. 각 선택지에는 판단 기준 설명을 함께 표시한다. 사용자가 자기 피부 타입을 확신하지 못해도 고를 수 있어야 한다.
6. 피부 타입은 이후 마이페이지에서 수정할 수 있어야 한다.

**Validation**

- 최소 1개 이상 선택
- `UNKNOWN`과 다른 값의 동시 저장 불가 (서버에서도 검증)

**Acceptance Criteria**

- 지성 + 민감성처럼 복수 선택이 저장된다.
- `모르겠음` 선택 시 다른 항목이 모두 해제된다.
- 아무것도 선택하지 않으면 다음 단계로 넘어갈 수 없다.

### F-ONBOARD-03. 생리 · 호르몬 정보 입력 `변경`

| 항목 | 내용 |
| --- | --- |
| 기능 ID | F-ONBOARD-03 |
| 기능명 | 생리 · 호르몬 정보 입력 |
| 설명 | 호르몬 변화에 따른 피부 패턴 분석을 위해 생리 상태와 주기 정보를 입력받는다. |
| 관련 화면 | S-04 |
| 우선순위 | M |
| 선행 조건 | F-ONBOARD-02 완료 **AND** 성별 = `FEMALE` |
| 입력 | 생리 상태, 최근 시작일, 평균 주기 |
| 출력 | 호르몬 관련 프로필 정보 |
| API 필요 | O |

**선택지 (단일 선택)**

| 값 | 라벨 |
| --- | --- |
| `MENSTRUATING` | 생리 |
| `HORMONE_PILL` | 호르몬약 |
| `HORMONE_INJECTION` | 주사 |
| `MENOPAUSE` | 폐경 |

**Business Rule**

1. **S-01의 성별이 `FEMALE`인 경우에만 이 화면으로 진입한다.** 그 외 성별은 S-02에서 곧바로 S-05로 이동한다.
2. 생리 상태는 단일 선택이다.
3. 최근 시작일은 날짜 선택 행으로 입력한다.
4. 평균 주기는 스테퍼로 입력하며 20~45일 범위, 기본값 28일이다.
5. `나중에 설정하기`로 건너뛸 수 있으며, 건너뛰어도 온보딩은 정상 완료된다.
6. 이 정보가 없어도 F-SKIN, F-ANALYSIS 등 핵심 기능은 정상 동작해야 한다.
7. 상태에 따라 하위 입력의 의미가 달라진다. `MENOPAUSE` 선택 시 최근 시작일 · 평균 주기 입력은 노출하지 않는다.

**Validation**

| 필드 | 규칙 |
| --- | --- |
| 생리 상태 | 선택 · 4종 중 1개 |
| 최근 시작일 | 선택 · 오늘 이후 날짜 불가 |
| 평균 주기 | 선택 · 20~45 정수 · 기본값 28 |

**Acceptance Criteria**

### F-HOME-01. 낮/밤 자동 판정 `변경`

| 항목 | 내용 |
| --- | --- |
| 기능 ID | F-HOME-01 |
| 기능명 | 낮/밤 자동 판정 |
| 설명 | 현재 시각을 기준으로 낮 홈과 밤 홈 중 어느 화면을 기본 노출할지 결정한다. |
| 관련 화면 | S-07, S-08 |
| 우선순위 | H |
| 트리거 | 홈 진입 / 앱 포그라운드 전환 |
| 입력 | 현재 시각 |
| 출력 | `DAY` 또는 `NIGHT` |
| API 필요 | O (홈 조회에 포함) |

**Business Rule**

1. 판정 기준은 **전 사용자 동일한 고정 시각**이다. 12시간 균등 분할.
    
    
    | 시간대 | 판정 | 화면 |
    | --- | --- | --- |
    | 06:00 ~ 17:59 | `DAY` | S-07 |
    | 18:00 ~ 05:59 | `NIGHT` | S-08 |
2. 사용자별 수면 시간을 판정에 사용하지 않는다. 온보딩에서 수면 시간 입력이 제거되었기 때문이다.
3. 앱이 백그라운드에서 다시 활성화될 때 시간대를 재판정한다.
4. 판정 기준 시각은 기기 시간을 사용한다.
5. 판정 로직은 단일 지점에 격리한다. 이후 루틴 기록 데이터가 쌓이면 이 부분만 개인화 로직으로 교체할 수 있어야 한다.

**Acceptance Criteria**

- 17:59에 진입하면 낮 홈, 18:00에 진입하면 밤 홈이 노출된다.
- 백그라운드에서 18:00을 넘긴 뒤 복귀하면 밤 홈으로 전환된다.

3. 각 날짜 셀은 점 2개(모닝 · 나이트)로 상태를 표현한다.
4. 오늘 날짜를 강조한다.
5. 가입 이전 기간은 `기록 없음` 상태로 표시한다.
6. 미래 날짜는 선택 불가 처리한다.

**Acceptance Criteria**

- 월 변경 시 선택한 월의 데이터만 표시된다.
- 모닝만 기록한 날과 둘 다 기록한 날이 시각적으로 구분된다.

**Acceptance Criteria**

- 모닝 제품 기록과 나이트 제품 기록이 서로 다른 기록으로 저장·표시된다.

### F-PRODUCT-04. 성분 확인 및 기록 저장 `변경`

| 항목 | 내용 |
| --- | --- |
| 기능 ID | F-PRODUCT-04 |
| 기능명 | 성분 확인 및 기록 저장 |
| 설명 | 제품 정보와 성분 목록을 확인시키고, 사용자가 확정하면 제품 기록을 저장한다. |
| 관련 화면 | S-14 |
| 우선순위 | H |
| 입력 | 제품 ID, 시간대 |
| 출력 | 제품 기록 |
| DB 영향 | 제품 사용 기록 생성, 사용자-제품 관계 갱신 |
| API 필요 | O |

**Business Rule**

1. **이 화면의 `기록 완료` 버튼이 제품 기록의 저장 시점이다.** 이전 단계에서는 저장하지 않는다.
2. 표시 항목: 제품명(큰 제목), 분류, 총 성분 개수, 주요 성분 섹션, 성분 목록.
3. 저장 시 진입 시 전달된 시간대(`MORNING` / `NIGHT`)를 함께 기록한다.
4. 신규 제품은 사용자 제품 목록에도 추가한다.
5. 기존 제품은 마지막 사용 시점을 갱신한다.
6. 저장 성공 후 기록 허브 상태를 갱신한다.
7. 화면 하단의 피부 기록 유도 카드는 조건부다. (F-PRODUCT-06)

**중복 처리**

같은 날짜, 같은 시간대에 같은 제품을 다시 기록하려는 경우:

> "이미 오늘 모닝에 기록한 제품이에요. 기존 기록을 갱신할까요?"
> 
- 확인 → 갱신
- 취소 → 기존 기록 유지

동일 날짜라도 시간대가 다르면 중복으로 보지 않는다. (모닝 토너 / 나이트 토너는 별개 기록)

**Acceptance Criteria**

- 저장 후 해당 시간대의 제품 기록 슬롯이 완료로 바뀐다.
- 성분 확인 화면을 이탈하면 기록이 저장되지 않는다.
- 동일 제품 중복 데이터가 의도치 않게 생성되지 않는다.

- 비교 데이터가 없어도 화면 오류가 발생하지 않는다.

### F-ANALYSIS-01. 성분-피부 변화 시간차 분석 `확정`

| 항목 | 내용 |
| --- | --- |
| 기능 ID | F-ANALYSIS-01 |
| 기능명 | 성분-피부 변화 시간차 분석 |
| 우선순위 | H |
| Actor | 시스템 |
| 트리거 | 신규 피부 분석 결과 저장 |
| 입력 | 제품 기록 + 피부 기록 |
| 출력 | 성분별 패턴 후보 |
| API 필요 | 내부 |

**Business Rule**

1. 제품에 포함된 성분 단위로 사용 이력을 생성한다.
2. 사용 후 1~7일 피부 변화를 추적한다.
3. 동일 방향 변화가 반복되는지 확인한다.
4. 반복성이 부족하면 패턴으로 확정하지 않는다.
5. 기록 3일 미만 사용자는 데이터 부족 상태로 처리한다.
6. 하루 2회 기록 구조를 고려해 모닝 사용 제품과 나이트 사용 제품의 노출 시점을 구분한다.

**확정 기준** (ADR 0009에서 수치 확정)

BR 3·4의 "반복"과 "부족"은 아래 세 조건을 **모두** 만족할 때만 확정으로 본다.

| 조건 | 값 |
| --- | --- |
| 관측 쌍 수 | 3건 이상 |
| 동일 방향 비율 | 67% 이상 |
| 평균 변화량 | 절대값 3점 이상 |

하나라도 못 넘으면 확정하지 않고 **"확인 중"** 상태로 남긴다. 목록에서 제거하지는 않는다.
이 상태는 REPORT-01의 `confidence: "OBSERVING"`으로 내려간다.

**계산 규칙** (ADR 0009, 모닝·나이트 분리는 ADR 0014)

- 사용일 D의 지표값을 기준선으로 D+1 ~ D+7의 값과 비교한다.
- **분석이 완료된(`COMPLETED`) 피부 기록만 관측으로 쓴다.** 실패·진행 중 기록의 지표는 믿을 수 없고,
  그 값이 기준선이 되면 실재하지 않는 변화를 패턴으로 잡는다.
- 하루 2건(모닝·나이트)은 평균으로 합치지 않고 **슬롯별로 분리**해 관측한다. 기준선과 D+lag 비교는
  같은 슬롯끼리만 한다 — 모닝 사용은 모닝 관측과, 나이트 사용은 나이트 관측과 비교한다.
- 같은 성분을 같은 날 모닝·나이트에 모두 썼으면 노출 **2건**(슬롯별)으로 센다.
- 기록 일수(데이터 부족 판정)는 여전히 날짜 단위로 센다 — 모닝·나이트 2건은 1일로 센다.
- 한 성분·지표에는 가장 강한 시차 하나만 인사이트로 남긴다.
- 분석은 새 피부 기록마다 전체 기간을 다시 계산하며, 이전 회차 결과를 대체한다.

> MVP에서는 이를 **인과관계 확정이 아니라 기록 기반 연관 패턴**으로 취급한다.
> 

> **알려진 한계** — 한 제품에 함께 든 성분들은 항상 같은 날 노출되므로 서로 구분되지 않는다.
> 이 경우 두 성분 모두 후보로 노출하며, 이는 의도된 동작이다.
>

> 걸치면 확정 임계값을 더 엄격하게 요구하고(BR 4), 확정되더라도 인사이트 신뢰도 점수를 낮춘다(BR 1).
> 생리 정보가 없으면 보정 없이 기존 임계값·신뢰도가 그대로 적용된다(BR 3). 구간 경계 비율은 근거

### F-ANALYSIS-04. 개인 성분 프로파일 생성 및 갱신 `확정`

| 항목 | 내용 |
| --- | --- |
| 기능 ID | F-ANALYSIS-04 |
| 기능명 | 개인 성분 프로파일 생성·갱신 |
| 우선순위 | H |
| 입력 | 분석 결과, 온보딩 피부 타입 |
| 출력 | 성분별 반응 상태 |

**분류**

| 값 | 라벨 |
| --- | --- |
| `GOOD` | 맞음 |
| `CAUTION` | 주의 |
| `INSUFFICIENT` | 데이터 부족 |

**Business Rule**

1. 충분한 데이터가 없는 성분을 임의로 맞음/주의로 판단하지 않는다.
2. 데이터가 누적될 때마다 상태를 재평가한다.
3. **온보딩에서 입력한 피부 타입을 초기 해석 기준으로 사용한다.** 기록이 쌓이기 전 판단 근거가 전무한 상태를 완화하기 위함이다.
4. 최신 프로파일을 구매 전 확인(F-CHECK)에서 재사용한다.

**판정 기준** (ADR 0010에서 수치 확정)

상태는 F-ANALYSIS-01이 **확정한** 패턴에서만 나온다. 확정 기준은 ADR 0009와 같다.

| 조건 | 상태 |
| --- | --- |
| 확정된 **악화** 패턴이 하나라도 있다 | `CAUTION` |
| 확정된 패턴이 **개선**뿐이다 | `GOOD` |
| 확정된 패턴이 없다 | `INSUFFICIENT` |

악화가 개선을 이긴다. 한 성분이 지표마다 다른 방향으로 확정될 때(예: 모공 개선 · 트러블 악화)
"맞음"으로 부르면 확정된 악화가 표시에서 사라지고, 그 판단이 구매로 이어지기 때문이다.

**피부 타입 반영** (BR 3 · ADR 0010)

민감성을 선택한 사용자에 한해 **악화 방향의 평균 변화량 기준만** 3점에서 2점으로 낮춘다.
관측 쌍 수와 동일 방향 비율은 완화하지 않으며, 개선 방향도 완화하지 않는다.

> **관측이 없는 성분은 피부 타입과 무관하게 `INSUFFICIENT`다.** 피부 타입만으로 성분 상태를 정하는 것은
> BR 1이 금지한 임의 분류다. 피부 타입은 이미 관측이 있는 성분의 판정 문턱만 조정한다. (ADR 0010)
>

**데이터 부족 성분의 처리**

사용 기록이 있으나 패턴이 확정되지 않은 성분도 `INSUFFICIENT` 상태로 남긴다. 사용 일수는 기록하고
판단 근거는 남기지 않는다. USER-02가 "이 성분을 몇 번 썼는데 아직 부족한지"를 보여주기 위함이다.

### F-ANALYSIS-05. 프로파일 완성도 계산 `확정`

| 항목 | 내용 |
| --- | --- |
| 기능 ID | F-ANALYSIS-05 |
| 기능명 | 프로파일 완성도 계산 |
| 우선순위 | H |
| 출력 | 완성도 퍼센트 |

**Business Rule**

1. 단순 가입 기간만으로 증가시키지 않는다.
2. 실제 분석 가능한 기록 축적량을 기반으로 계산한다.
3. 완성도 100%가 모든 화장품 성분에 대한 절대적 판단 완료를 의미해서는 안 된다.
4. 마이페이지(S-23)의 완성도 게이지와 구매 전 확인 화면이 같은 값을 사용한다.

**산출식** — 두 축을 각각 목표치에서 포화시킨 뒤 동일 가중으로 평균한다. (ADR 0011)

```
A 기록 충분성  = min(기록 일수 / 30, 1.0)
B 성분 커버리지 = min(확정 성분 수 / 20, 1.0)

completionRate = round((A * 0.5 + B * 0.5) * 100)
```

- **기록 일수** — 피부 기록이 존재하는 서로 다른 날의 수. 모닝·나이트 2건은 1일로 센다.
  가입 후 경과일이 아니다. (BR 1)
- **확정 성분 수** — 반응 상태가 `맞음` 또는 `주의`인 성분. `데이터 부족`은 세지 않는다. (BR 2)
- 결과는 0~100 정수다.

100%의 의미는 "모든 성분을 판단했다"가 아니라 **"개인화된 판단을 하기에 충분한 데이터가 모였다"**다.
분모가 성분 마스터 전체가 아니므로 "전체 성분 대비"라는 의미는 성립하지 않는다. (BR 3)

목표치 30일 · 20종은 근거 없는 초기값이며 실사용 데이터가 쌓이면 재검토한다.

### F-CHECK-03. 개인화 위험도 산출 `확정`

| 항목 | 내용 |
| --- | --- |
| 기능 ID | F-CHECK-03 |
| 기능명 | 개인화 위험도 산출 |
| 설명 | 제품 성분과 사용자 성분 프로파일을 비교해 위험도를 계산한다. |
| 우선순위 | H |
| 입력 | 제품 성분 + 개인 성분 프로파일 |
| 출력 | 위험도 등급 + 근거 성분 |

**위험도**

| 값 | 라벨 | 설명 |
| --- | --- | --- |
| `LOW` | 잘 맞아요 | 내 피부 기준으로 주의할 성분이 없어요 |
| `MEDIUM` | 보통이에요 | 내 피부 기준으로 주의할 성분이 일부 있어요 |
| `HIGH` | 주의가 필요해요 | 내 피부 기준으로 맞지 않는 성분이 포함되어 있어요 |

**Business Rule**

1. 제품 전체 성분을 개인 프로파일과 비교한다.
2. `CAUTION` 성분을 식별하고, 그 수와 비중을 위험도 판단에 사용한다.
   **산출 기준(ADR 0015)**: 비중의 분모는 판정된 성분(`SUITABLE`+`CAUTION`)만이다.
   `CAUTION` 수 ≥3건이거나, 판정 성분이 5종 이상이고 비중 ≥40%면 `HIGH`. `CAUTION`이 1건이라도
   있으면 최소 `MEDIUM`. 두 축 중 더 심각한 등급을 최종 등급으로 한다. 임계값에 이론적 근거는
   없으며(ADR 0009·0010·0011과 같은 성격), 실기록이 쌓이면 재검토한다.
3. 개인 기록 근거가 존재하면 성분별 사유를 함께 생성한다. (예: 과거 홍조 반응 있음)
   근거 문구가 없으면 확정 성분이라도 지어내지 않고 비워 둔다.
4. `INSUFFICIENT` 성분은 위험도를 임의로 높이거나 낮추지 않는다.
   비중 계산의 분모에서 제외하는 것으로 보장한다 — 분모에 포함하면 판정되지 않은 성분이 늘수록
   비중이 낮아져 위험도를 낮추는 결과가 되므로(ADR 0015 맥락).
5. **이 제품의 성분 중 판정된 것이 하나도 없으면**(전체 프로파일이 아니라 이 제품 기준) 위험도를
   계산하지 않고 데이터 부족 상태(`CHECK_PROFILE_NOT_READY`)를 반환한다. 이 경우 평가를 저장하지
   않는다.

### F-MY-03. 성분 전체 보기 `신규`

| 항목 | 내용 |
| --- | --- |
| 기능 ID | F-MY-03 |
| 기능명 | 성분 전체 보기 |
| 설명 | 요약에 노출되지 않은 성분까지 전체 목록으로 확인한다. |
| 관련 화면 | S-23 → **신규 화면(제작 요청 완료)** |
| 우선순위 | M |

**Business Rule**

1. 마이페이지에는 `성분 전체 보기` 행만 두고 상세는 별도 화면에서 처리한다.
2. 상태별(맞음 / 주의 / 데이터 부족) 필터를 제공하는 것을 권장한다.
   USER-02의 `status` 쿼리 파라미터로 서버에서 거른다.
3. 목록 순서는 맞음 → 주의 → 데이터 부족이며, 그룹 안에서는 노출 일수가 많은 성분이 앞에 온다.
4. **데이터 부족 성분에는 판단 근거를 표시하지 않는다.** 대신 노출 횟수를 보여 왜 아직 부족한지
   알 수 있게 한다. 서버가 근거를 `null`로 내려준다.
5. 아직 판단된 성분이 없으면 빈 목록이다. 오류 화면이 아니라 안내 문구로 처리한다.

### F-SYSTEM-04. 상태 표기 접근성 규칙 `신규`

| 항목 | 내용 |
| --- | --- |
| 기능 ID | F-SYSTEM-04 |
| 설명 | 완료/미완료, 맞음/주의 등 상태를 색만으로 구분하지 않는다. |
| 우선순위 | H |

**Business Rule**

1. 색만으로 상태를 구분하면 적록색약 사용자에게 두 상태가 같게 보인다. **색과 기호를 반드시 병행한다.**
2. 적용 대상
    - 기록 슬롯 완료/미완료 (초록 + 체크 / 빨강 + 빈 원)
    - 캘린더 날짜 점 (채움 / 외곽선 / 흐림)
    - 성분 배지 (맞음 / 주의 / 데이터 부족 — 텍스트 병기)
    - 위험도 등급 (색 + 텍스트 등급명)
3. 흑백으로 렌더링해도 상태 구분이 가능해야 한다.
