# 공통응답포맷 + 예외처리 코드 (최종)

# 1. 공통 응답 포맷

## 1.1 응답 구조

모든 API는 성공·실패 관계없이 아래 4개 필드를 갖는 동일한 envelope를 사용한다.

json

```json
{
  "isSuccess": true,
  "code": "COMMON_SUCCESS",
  "message": "요청에 성공했습니다.",
  "result": {}
}
```

| 필드 | 타입 | Null 허용 | 설명 |
| --- | --- | --- | --- |
| `isSuccess` | Boolean | X | 요청 성공 여부 |
| `code` | String | X | 서비스 내부 응답 코드 |
| `message` | String | X | 사용자에게 그대로 노출 가능한 메시지 |
| `result` | Object / Array / Null | O | 실제 응답 데이터 |

**규칙**

1. envelope 필드는 이 4개로 **고정**한다. 특정 API를 위해 최상위 필드를 추가하지 않는다.
2. 추가 정보가 필요하면 `result` 내부에 넣는다.
3. `message`는 사용자 노출을 전제로 작성한다. 스택 트레이스, 내부 식별자, 영문 예외명을 담지 않는다.
4. 프론트는 **HTTP Status가 아니라 `code`로 분기**한다. Status는 네트워크 계층 처리용이다.

## 1.2 성공 응답

### 조회 성공

json

```json
{
  "isSuccess": true,
  "code": "COMMON_SUCCESS",
  "message": "조회에 성공했습니다.",
  "result": {}
}
```

### 생성 성공 — HTTP 201

json

```json
{
  "isSuccess": true,
  "code": "COMMON_CREATED",
  "message": "생성에 성공했습니다.",
  "result": {
    "recordId": 31
  }
}
```

> 생성 API는 **생성된 리소스의 ID를 반드시 반환**한다. 프론트가 후속 화면(S-14 → 기록 허브 갱신, S-18 → 리포트 이동)으로 넘어갈 때 필요하다.
>

```json
  "message": "수정에 성공했습니다.",
  "result": null
}
```

### 삭제 성공

json

## 1.3 실패 응답

json

```json
{
  "isSuccess": false,
  "code": "AUTH_INVALID_TOKEN",
  "message": "다시 로그인해주세요.",
  "result": null
}
```

실패 응답의 `result`는 원칙적으로 `null`이다. 단, Validation 오류와 재시도 힌트가 필요한 경우에만 객체를 담는다.

## 1.4 Validation 오류 — HTTP 422

여러 입력값이 동시에 잘못된 경우도 한 번에 반환할 수 있도록 `errors` 배열을 사용한다.

json

```json
{
  "isSuccess": false,
  "code": "COMMON_VALIDATION_FAILED",
  "message": "입력값이 올바르지 않습니다.",
  "result": {
    "errors": [
      { "field": "name", "reason": "이름은 필수입니다." },
      { "field": "age", "reason": "나이는 10~100 사이여야 합니다." }
    ]
  }
}
```

**규칙**

1. 필드가 하나여도 `errors` 배열 형태를 유지한다. 프론트 분기 코드가 단순해진다.
2. `field`는 요청 Body의 필드명과 정확히 일치시킨다. 중첩 필드는 점 표기를 쓴다. (`period.startDate`)
3. `reason`은 사용자에게 그대로 보여줄 수 있는 문장으로 작성한다.
4. 도메인 특화 검증(예: 피부 타입 배타 규칙)은 `COMMON_VALIDATION_FAILED` 대신 **전용 코드**를 사용한다. 프론트가 어떤 UI를 띄울지 달라지기 때문이다.

json

```json
{
  "isSuccess": false,
  "code": "ONBOARD_SKIN_TYPE_CONFLICT",
  "message": "'모르겠음'은 다른 피부 타입과 함께 선택할 수 없어요.",
  "result": {
    "errors": [
      { "field": "skinTypes", "reason": "UNKNOWN은 단독으로만 선택할 수 있습니다." }
    ]
  }
}
```

## 1.5 부분 실패 응답 `신규`

홈(S-07/S-08)처럼 여러 소스를 합쳐 내려주는 BFF 응답에서, 일부 외부 API가 실패해도 **응답 전체를 실패로 만들지 않는다.**

> 기능명세서 F-HOME-03 · F-SYSTEM-03: 일시적인 외부 API 장애가 앱 전체 장애로 확산되지 않도록 영역 단위로 격리한다.
> 

json

```json
{
  "isSuccess": true,
  "code": "COMMON_SUCCESS",
  "message": "조회에 성공했습니다.",
  "result": {
    "homeType": "DAY",
    "environment": null,
    "routineRecommendation": [ ... ],
    "failedSections": [
      {
        "section": "environment",
        "code": "WEATHER_API_FAILED",
        "message": "날씨 정보를 불러오지 못했어요."
      }
    ]
  }
}
```

**규칙**

1. `isSuccess`는 `true`를 유지한다. 핵심 데이터가 정상 조회되었기 때문이다.
2. 실패한 영역의 값은 `null`로 내린다. 빈 객체(`{}`)를 쓰지 않는다. "값이 없음"과 "조회 실패"를 구분해야 한다.
3. `failedSections`는 실패가 없으면 **빈 배열**로 내린다. 필드 자체를 생략하지 않는다.
4. 프론트는 해당 영역만 오류 상태로 렌더링하고 나머지는 정상 표시한다.
5. **핵심 데이터가 실패하면 부분 실패가 아니라 전체 실패로 처리한다.** 예를 들어 사용자 조회 자체가 실패하면 홈 응답 전체를 실패로 내린다.

**적용 대상 API**

| API | 부분 실패 허용 영역 |
| --- | --- |
| 홈 조회 | `environment` (날씨·자외선) |
| 리포트 조회 | `insights` (분석 파이프라인) |
| 쇼핑 홈 | `recommendations` (프로파일 기반 추천) |

# 2. HTTP Status 규칙

| HTTP | 의미 | 사용 상황 |
| --- | --- | --- |
| 200 | OK | 조회 / 수정 / 삭제 성공, 부분 실패 포함 |
| 201 | Created | 생성 성공 |
| 400 | Bad Request | 형식 자체가 잘못된 요청, 지원하지 않는 파라미터 |
| 401 | Unauthorized | 인증 실패 · 토큰 문제 |
| 403 | Forbidden | 인증은 되었으나 접근·수정 권한 없음 |
| 404 | Not Found | 리소스 없음 |
| 409 | Conflict | 상태 충돌 · 중복 · 데이터 부족으로 처리 불가 |
| 422 | Unprocessable Entity | 형식은 맞으나 값이 유효하지 않음 |
| 500 | Internal Server Error | 서버 내부 오류 |
| 503 | Service Unavailable | 외부 API 장애 |
| 504 | Gateway Timeout | 외부 API 응답 지연 `신규` |

**400 vs 422 구분 기준**

|  | 400 | 422 |
| --- | --- | --- |
| 판단 시점 | 파싱 단계 | 검증 단계 |
| 예시 | `timeSlot=AFTERNOON` (Enum에 없는 값) | `age=150` (타입은 맞으나 범위 초과) |
| 예시 | JSON 파싱 실패 | `productIds=[]` (최소 1개 위반) |

**409의 의미**

409는 "요청은 올바르지만 지금 상태에서는 처리할 수 없다"를 뜻한다. 클라이언트가 요청을 고쳐서 재시도해도 소용없고, **상태가 바뀌어야 해결되는** 경우에 쓴다.

- 이미 기록한 슬롯에 다시 기록 → `PRODUCT_ALREADY_RECORDED_IN_SLOT`
- 프로파일 데이터가 아직 부족함 → `CHECK_PROFILE_NOT_READY`

# 3. 응답 코드 규칙

## 3.1 명명 규칙

```
{도메인}_{의미}
```

- 영문 대문자 + 언더스코어
- **숫자를 사용하지 않는다**

`AUTH401` / `AUTH402` / `AUTH403` 보다
`AUTH_INVALID_TOKEN` / `AUTH_TOKEN_EXPIRED` / `AUTH_REFRESH_TOKEN_EXPIRED` 가 훨씬 읽기 쉽기 때문이다. 코드만 보고 원인을 알 수 있어야 로그 검색과 프론트 분기가 편해진다.

## 3.2 도메인 목록

| 도메인 | 범위 | 대응 기능 |
| --- | --- | --- |
| `COMMON` | 전역 공통 | F-SYSTEM-* |
| `AUTH` | 인증 · 토큰 | F-AUTH-* |
| `USER` | 사용자 · 프로필 · 설정 | F-MY-* |
| `ONBOARD` `신규` | 온보딩 단계 · 입력 규칙 | F-ONBOARD-* |
| `WEATHER` | 날씨 · 자외선 · 위치 | F-HOME-03 |
| `RECORD` `신규` | 기록 허브 · 슬롯 · 캘린더 | F-RECORD-* |
| `PRODUCT` | 제품 · 성분 마스터 | F-PRODUCT-02, 04 |
| `PRODUCT_RECORD` | 제품 사용 기록 | F-PRODUCT-04, 06 |
| `ROUTINE` | 루틴 | F-PRODUCT-05, 06 |
| `SCAN` | 제품 스캔 | F-PRODUCT-03 |
| `SKIN` | 피부 기록 · 촬영 · 분석 | F-SKIN-* |
| `ANALYSIS` | 분석 파이프라인 · 프로파일 | F-ANALYSIS-* |
| `CHECK` | 구매 전 확인 | F-CHECK-* |
| `REPORT` | 리포트 · 인사이트 | F-REPORT-* |
| `PERMISSION` | OS 권한 (클라이언트 전용) | F-SYSTEM-01 |

## 3.3 금지 사항

1. 같은 의미의 코드를 도메인마다 중복 정의하지 않는다. 공통으로 쓸 수 있으면 `COMMON_*`을 쓴다.
2. 하나의 코드를 여러 원인에 재사용하지 않는다. 프론트가 안내 문구를 분기할 수 없게 된다.
3. 코드에 화면 ID나 API 이름을 넣지 않는다. (`S14_SAVE_FAILED` 같은 형태 금지)

# 4. Success Code

| Code | HTTP | Message |
| --- | --- | --- |
| `COMMON_SUCCESS` | 200 | 요청에 성공했습니다. |
| `COMMON_CREATED` | 201 | 생성에 성공했습니다. |

성공 코드는 이 2개만 사용한다. 도메인별 성공 코드를 만들지 않는다. 성공 시 프론트가 분기해야 할 정보는 `result` 안에 담는다.

> **범례**`신규` v2에서 추가 · `변경` v1에서 의미나 이름이 바뀜 · 표기 없음은 v1 유지

>

### `PRODUCT_ALREADY_RECORDED_IN_SLOT` 상세

v1의 `PRODUCT_ALREADY_RECORDED_TODAY`를 대체한다. 중복 판정 기준이 **날짜**에서 **날짜 + 시간대**로 바뀌었기 때문이다.

| 상황 | v1 판정 | v2 판정 |
| --- | --- | --- |
| 모닝에 토너 기록 → 나이트에 같은 토너 기록 | 중복 | **정상** |
| 모닝에 토너 기록 → 모닝에 같은 토너 재기록 | 중복 | 중복 |

이 코드는 오류이지만 **사용자에게 실패로 보여주지 않는다.** 기능명세서 F-PRODUCT-04의 중복 처리 정책에 따라 갱신 여부를 묻는 확인 팝업을 띄운다.

json

```json
{
  "isSuccess": false,
  "code": "PRODUCT_ALREADY_RECORDED_IN_SLOT",
  "message": "이미 오늘 모닝에 기록한 제품이에요. 기존 기록을 갱신할까요?",
  "result": {
    "recordId": 31,
    "timeSlot": "MORNING",
    "duplicatedProductIds": [11, 15]
  }
}
```

프론트는 `duplicatedProductIds`로 어떤 제품이 겹쳤는지 표시하고, 사용자가 확인하면 수정 API를 호출한다.

# 6. Enum 사전

> 모든 Enum은 **문자열(String)** 로 전달한다. 숫자 Enum은 사용하지 않는다.
`{ "gender": 0 }` 보다 `{ "gender": "FEMALE" }` 이 의미가 명확하고 Swagger 문서도 읽기 쉽다.
>

| Enum | 값 | 라벨 | 관련 |
| --- | --- | --- | --- |
| `Gender` | `FEMALE` | 여성 | F-ONBOARD-01 |
|  | `MALE` | 남성 |  |
|  | `UNSPECIFIED` | 선택 안 함 |  |
| `SkinType` `신규` | `OILY` | 지성 | F-ONBOARD-02 |

# 7. 오류로 처리하지 않는 상황 `신규`

> 아래는 모두 **정상 응답(200 + `isSuccess: true`)** 으로 처리한다. 오류 코드를 반환하면 프론트가 불필요한 오류 화면을 띄우게 된다.
> 

| 상황 | 응답 | 화면 처리 |
| --- | --- | --- |
| 저장된 제품 0건 | `result: []` | 빈 상태 + 검색/스캔 유도 (S-11) |
| 검색 결과 0건 | `result: []` | 결과 없음 안내 (S-12) |
| 루틴 0건 | `result: []` | 루틴 섹션 생략 (S-11) |
| 오늘 기록 없음 | 각 슬롯 `completed: false` | 미완료 상태 표시 (S-09/10) |
| 비교할 이전 기록 없음 | `changes: null` | 전일 대비 문구 생략 (S-18) |
| 인사이트 0건 | `insights: []` | 인사이트 카드 생략 (S-19) |
| 프로파일 완성도 0% | `profileCompletion: 0` | 게이지 0% 표시 (S-23) |
| 성분 상태가 데이터 부족 | `status: "INSUFFICIENT"` | 데이터 부족 배지 (S-23) |
| 리포트 요약 카드 조건 미충족 | `todayReport: null` | 카드 미노출 (S-08) |

**판단 기준**

> "데이터가 없다"는 오류가 아니다. **"데이터를 가져오지 못했다"만 오류다.**
> 

이 구분이 흐려지면 신규 사용자가 앱을 처음 켰을 때 온 화면이 오류로 뒤덮인다. 특히 이 서비스는 기록이 누적되어야 값이 생기는 구조라 **초기 사용자는 대부분의 영역이 비어 있는 게 정상**이다.

# 8. 공통 데이터 규칙

## 8.1 날짜 · 시간

모든 날짜/시간은 **ISO-8601**을 사용한다.

| 용도 | 형식 | 예시 |
| --- | --- | --- |
| 일시 | `yyyy-MM-dd'T'HH:mm:ssXXX` | `2026-08-07T14:30:00+09:00` |
| 날짜 | `yyyy-MM-dd` | `2026-08-07` |
| 시각 | `HH:mm` | `23:00` |
| 연월 | `yyyy-MM` | `2026-08` |

**규칙**

1. 타임존은 `+09:00`(KST)을 명시한다. 생략하거나 UTC로 보내지 않는다.
2. **`NIGHT` 슬롯 기록은 "밤이 시작된 날짜"로 귀속한다.** 18:00~23:59에 기록하면 그날 날짜, 자정을 넘겨 00:00~05:59에 기록해도 **전날 날짜**로 저장한다. 밤 홈·나이트 탭이 뜨는 18:00~05:59 구간 전체(F-HOME-01의 `NIGHT` 판정 구간)를 하나의 밤으로 취급하기 위함이다.
3. `MORNING` 슬롯은 자정을 넘길 일이 없으므로 기록 시각의 달력 날짜를 그대로 사용한다.
4. 낮/밤 판정(F-HOME-01)은 클라이언트 기기 시간을 사용하되, **기록의 날짜 귀속(위 2·3번 규칙)은 서버 시간을 기준**으로 계산한다.

**`NIGHT` 슬롯 날짜 계산**

```
서버 시각의 시(hour)가 00~05시  → 서비스 날짜 = 서버 날짜 - 1일
서버 시각의 시(hour)가 18~23시  → 서비스 날짜 = 서버 날짜 그대로
```

> 예: 8월 7일 23:40에 나이트 루틴을 기록 → `2026-08-07`로 저장. 같은 밤 이어서 8월 8일 01:20에 나이트 피부 기록을 남겨도 → 마찬가지로 `2026-08-07`로 저장한다. 다음 날 아침 모닝 기록은 정상적으로 `2026-08-08`이다.
> 
> 
> **결정 배경 (기존 TBD 해소)** — 기존 규칙(달력 자정 기준)대로면 같은 밤 안에서도 자정 전/후 기록이 서로 다른 날짜로 쪼개져, `PRODUCT_ALREADY_RECORDED_IN_SLOT` · `SKIN_ALREADY_RECORDED_IN_SLOT` 같은 슬롯 중복 판정과 F-SKIN-05의 "전일 동일 시간대 비교"가 어긋날 수 있었다. 위 규칙으로 하루 2슬롯(모닝·나이트) 구조와 일치시킨다.
> 

## 8.2 ID

모든 식별자는 `Long`을 사용한다.

```
userId · productId · ingredientId · routineId
productRecordId · skinRecordId · checkId · insightId
```

## 8.3 Null 처리

| 상황 | 반환 |
| --- | --- |
| 목록 조회 결과 없음 | `[]` |
| 단일 객체 없음 | `null` |
| 조회 실패 (부분 실패) | `null` + `failedSections` 등록 |

목록에 `null`을 사용하지 않는다. 프론트에서 `?.map()` 방어 코드가 사라진다.

## 8.4 필드 명명

- Request / Response 모두 **camelCase**
- Boolean은 `is` 또는 `has` 접두 또는 형용사형 (`isSuccess`, `saved`, `completed`)
- 배열 필드는 복수형 (`productIds`, `skinTypes`, `ingredients`)

# 10. 프론트엔드 처리 가이드

## 10.1 오류 표현 방식

| 유형 | UI | 대상 코드 |
| --- | --- | --- |
| 무음 처리 | 사용자에게 노출 없음 | `AUTH_TOKEN_EXPIRED` (자동 갱신 후 재시도) |
| 인라인 | 입력 필드 하단 문구 | `COMMON_VALIDATION_FAILED`, `ONBOARD_*` |
| 토스트 | 짧은 안내 | `PRODUCT_INVALID_KEYWORD`, `ROUTINE_EMPTY` |
| 확인 팝업 | 사용자 선택 필요 | `PRODUCT_ALREADY_RECORDED_IN_SLOT`, `ROUTINE_TIME_SLOT_MISMATCH` |
| 영역 오류 | 해당 카드만 오류 상태 | `failedSections` 내 코드 |
| 빈 상태 안내 | 오류가 아닌 안내 UI | `ANALYSIS_DATA_INSUFFICIENT`, `CHECK_PROFILE_NOT_READY`, `REPORT_DATA_INSUFFICIENT` |
| 전면 오류 | 재시도 버튼 포함 | `COMMON_SERVER_ERROR`, `*_FAILED` (500대) |
| 화면 이동 | 강제 이동 | `AUTH_REFRESH_TOKEN_EXPIRED` → S-00, `WEATHER_LOCATION_REQUIRED` → S-24 |

> **빈 상태 안내로 분류된 3개 코드에 빨간 오류 UI를 쓰지 마세요.** 기록이 부족한 건 신규 사용자의 정상 상태입니다.
> 

## 10.2 재시도 정책

| 구분 | 정책 |
| --- | --- |
| 500 / 503 / 504 | 자동 재시도 최대 2회, 지수 백오프(1s → 3s). 이후 사용자 재시도 버튼 |
| 401 `AUTH_TOKEN_EXPIRED` | 토큰 갱신 후 원 요청 1회 재시도. 갱신 실패 시 S-00 |
| 400 / 403 / 404 / 409 / 422 | **자동 재시도 금지.** 동일 요청은 동일 결과 |
| 저장 API (`POST`) | 자동 재시도 금지. 중복 저장 위험이 있으므로 사용자 명시적 재시도만 허용 |

## 10.3 입력값 보존

기능명세서 F-SYSTEM-03에 따라, **사용자 입력 직후 저장이 실패하면 입력 데이터를 유지**한다.

적용 필수 화면: S-01, S-02, S-04 (온보딩 입력), S-14 (선택한 제품), S-24 (선택한 지역)
