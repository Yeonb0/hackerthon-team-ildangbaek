# 0006. 임시 인증 — `X-User-Id` 헤더

- 상태: **부분 대체됨** → [ADR 0017](0017-임시-인증-토큰-통합.md)(헤더를 `X-User-Id`에서 목업
  Bearer 토큰으로 교체). 리졸버 패턴·"배포 전 필수 교체" 경고 등 나머지 결정은 유효.
- 날짜: 2026-08-08
- 담당: B
- 관련: STATUS.md 5장 블로커 #1, AUTH-01~03(A 담당), SKIN-01

## 맥락

`/health`를 제외한 **모든 API가 "인증 필요"**인데 인증 인프라가 없다. `spring-boot-starter-security`
의존성조차 없고 `SecurityFilterChain`·필터·`@AuthenticationPrincipal` 어느 것도 존재하지 않는다.
`userId`를 얻을 방법이 없으니 어떤 도메인 API도 착수할 수 없다.

인증 본체(AUTH-01~03)는 **A 담당**이다. B가 이를 함께 구현하면 담당 범위가 겹치고, 나중에 두 구현을
합칠 때 충돌한다. 그렇다고 A의 완료를 기다리면 **SKIN-01에 걸린 B의 후속 작업 전체**
(F-ANALYSIS → CHECK → REPORT)가 멈춘다.

## 결정

**`X-User-Id` 헤더에서 사용자 ID를 읽는 `@CurrentUserId` 리졸버를 임시로 둔다.**

```java
public ApiResponse<SkinRecordResponse> create(@CurrentUserId Long userId, ...)
```

- 위치: `global/auth/` — `CurrentUserId` · `CurrentUserIdArgumentResolver`
- 헤더가 없거나 숫자가 아니면 `401 COMMON_UNAUTHORIZED`
- `WebConfig.addArgumentResolvers`에 등록

## 근거

1. **획득 지점을 한 곳에 가둔다.** 컨트롤러는 `@CurrentUserId Long userId`만 안다. 인증이 붙으면
   리졸버 내부를 토큰 검증으로 바꾸는 것으로 끝나고 **컨트롤러·서비스·DTO는 건드리지 않는다.**
   각 컨트롤러가 헤더를 직접 읽었다면 전부 고쳐야 했다.
2. **A의 작업과 충돌하지 않는다.** 리졸버는 인증 방식을 규정하지 않는다. A가 JWT를 어떤 형태로
   만들든 이 인터페이스 뒤로 들어온다.
3. **되돌리기 쉽다.** 삭제 대상이 두 클래스와 등록 한 줄로 명확하다.

## ⚠️ 보안 위험 — 배포 전 필수 교체

**이 방식은 인증이 아니다.** `X-User-Id: 2`로 보내면 누구나 2번 사용자로 행세할 수 있다.
검증도 서명도 없다. 다음 중 하나라도 해당하면 **절대 사용해서는 안 된다.**

- 공개 인터넷에 노출된 환경
- 실제 사용자 데이터가 있는 환경
- 시연 외 목적의 상시 운영 환경

로컬 개발과 내부 시연에 한정한다. **AUTH-01이 완료되는 즉시 제거한다.**

## 결과

- SKIN-01을 포함한 B 담당 API를 인증 완료 전에 착수할 수 있다.
- 교체 시 변경 범위는 `CurrentUserIdArgumentResolver` 한 클래스다.
- 이 결정을 대체하는 새 ADR은 인증 도입 시 A가 작성한다.
