# 0018. 쇼핑 홈 3분류 및 오늘 컨텍스트 — category · todayContext

- 상태: **제안**
- 날짜: 2026-08-14
- 담당: B
- 관련: F-CHECK-01, ADR 0016, CHECK-01, HOME-01

## 맥락

프론트가 Figma "최종" 페이지 기준으로 SHOP-01(쇼핑 홈) 추천 영역을 3개 섹션(오늘 필요해요 ·
보습이 필요할 때 · 나에게 맞는 성분)으로 나눠 보여주고 싶다고 요청했다(`backend-request-shop01-and
-product-autofill.md`, 2026-08-14). 그러나 현재 `CHECK-01`(`GET /checks/home`)은 `recommendations`
단일 배열 + `reason` 텍스트만 내려주고, 3분류의 근거가 되는 원본 데이터(오늘 트러블·홍조 점수,
오늘 습도)도 이 API엔 없다.

요청 시점에 `boyeon`(프론트 메인) 브랜치의 실제 `ShoppingScreen.tsx`를 확인한 결과, 이 3분류 UI는
아직 화면에 구현되지 않은 상태였다(현재는 "나에게 맞는 제품" 단일 섹션만 있음). 프론트 화면
개편은 별도 일정으로 진행하기로 하고, 이 ADR은 **백엔드 API만 먼저 준비**하는 것을 전제로 한다
(관리자 결정, 2026-08-14).

## 결정

### 1. 옵션 A(응답에 분류 필드 추가)를 채택한다

`CheckRecommendationResponse`에 `category` 필드를, `CheckHomeResponse`에 `todayContext` 객체를
추가한다. 매칭 규칙(ADR 0016 — GOOD 성분 · key_ingredient · 제품 단위 dedup)은 그대로 두고, 그
위에 분류 레이어를 얹는다.

```
todayContext = {
  troubleScore: 오늘(가장 최근) 피부 기록의 TROUBLE 점수 또는 null,
  rednessScore: 오늘(가장 최근) 피부 기록의 REDNESS 점수 또는 null,
  humidity: 오늘 DailyEnvironment.humidity 또는 null,
  humidityGrade: DRY/NORMAL/HUMID 또는 null,
}
```

오늘 피부 기록이 없거나 오늘 환경 데이터가 없으면 해당 그룹의 필드는 개별적으로 `null`이다 —
HOME-01의 `environment` null 처리와 같은 방식이다.

### 2. category는 제품 카테고리 기준 추정 매칭이다

```
troubleScore >= 50 또는 rednessScore >= 50
  그리고 product.category ∈ {CLEANSER, TONER, SERUM}
    → TODAY_NEEDED

humidityGrade == DRY
  그리고 product.category ∈ {CREAM}
    → HUMIDITY_CARE

그 외 (기본값)
    → MATCHED_INGREDIENT
```

우선순위는 `TODAY_NEEDED` > `HUMIDITY_CARE` > `MATCHED_INGREDIENT` — 제품은 항상 정확히 1개
분류만 받는다(ADR 0016의 "제품 단위 1건" 철학과 일관되게, 분류도 제품당 1개로 좁힌다).

**이 매칭 기준에는 확정 근거가 없다.** 요청서도 "트러블·홍조가 어떤 성분/카테고리와 연결되는지"
"습도가 어떤 카테고리와 연결되는지"를 정하지 않았다. 임계값(50)과 카테고리 매핑은 추정치이며,
실사용 데이터·기획 확정 전까지 재검토 대상이다.

### 3. 임계값·카테고리 매핑은 이 ADR 밖에서 다시 정할 수 있다

`TODAY_NEEDED_SCORE_THRESHOLD`(50), `TODAY_NEEDED_CATEGORIES`, `HUMIDITY_CARE_CATEGORIES`는
`CheckHomeService`에 상수로 고정돼 있다. 프론트 3분류 화면이 실제로 붙는 시점에 기획 확인 후
값만 바꾸면 된다 — 매칭 **형태**(제품당 1분류, 우선순위 규칙)는 이 ADR이 고정하지만 **값**은
아니다.

## 근거

1. **옵션 A를 택한 이유.** 요청서 자체가 "프론트 입장에서는 이게 유일하게 호환됨"이라고 명시했다.
   옵션 B(분류 없이 컨텍스트만 전달)는 프론트가 `reason` 텍스트 키워드 매칭으로 분류해야 해서
   정확도가 낮고, 문구가 바뀌면 바로 깨진다.
2. **제품 카테고리로 추정한 이유.** 트러블·홍조·습도가 실제로 어떤 성분과 연관되는지는
   F-ANALYSIS 계열(성분-피부 시차 분석)의 영역이지만, 이 API는 이미 등록된 GOOD 성분 매칭
   제품 후보 안에서만 분류하면 되므로, 성분 단위 분석 없이 제품의 표시 카테고리만으로 충분히
   근사할 수 있다고 판단했다. 정확한 매칭은 아니다.
3. **null 허용 이유.** 오늘 피부 기록이 없는 사용자, 환경 데이터가 없는 사용자가 있을 수 있다
   (ADR 0011 BR 4의 완성도 계산과 마찬가지로 "없는 데이터를 지어내지 않는다"는 원칙,
   CLAUDE.md §2).
4. **화면이 아직 없는데 API를 먼저 만드는 이유.** 관리자 결정으로 백엔드 우선 구현을
   확정했다(2026-08-14). 프론트가 화면을 붙일 때 스키마가 이미 있으면 병렬 진행이 가능하다.

## 결과

- `CheckHomeService`(`api/check/service`)가 이 규칙을 구현한다.
- `HumidityGrade`(`domain/environment/entity`, 신규) — 습도 등급 계산. 임계값(40/70)도
  추정치이며 재검토 대상이다.
- `RecommendationCategory`(`api/check/dto`, 신규), `TodayContextResponse`(`api/check/dto`, 신규).
- `CheckHomeResponse.todayContext`, `CheckRecommendationResponse.category` 필드 추가로
  **CHECK-01 응답 스키마가 변경**된다. 기존 클라이언트가 있다면 하위 호환 확인이 필요하지만,
  현재 `boyeon`의 `ShoppingScreen.tsx`는 `recommendations[].category`·`todayContext`를 아직
  참조하지 않으므로 즉시 깨지는 곳은 없다.
- 이 ADR은 분류 **형태**만 고정한다 — 임계값·카테고리 매핑 **값**은 기획 확정 전까지 잠정치다.
