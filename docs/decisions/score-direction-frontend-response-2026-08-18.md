# 피부 지표 점수 방향성 요청 답변

작성일: 2026-08-18
대상 요청: 프론트 추가 요청 중 `지표 점수 방향 수정`

## 결론

현재 제출까지 남은 기간과 구현 범위를 고려하면, 백엔드는 **1번 방향**으로 처리하는 것을 제안한다.

- 개별 피부 지표 점수: 높을수록 좋은 상태
- 종합 점수: 높을수록 좋은 상태
- 디자인/프론트 문구: 점수의 의미가 바로 보이도록 `트러블 안정도`, `홍조 안정도`, `수분 컨디션`처럼 긍정 방향의 지표명으로 표현

즉, 백엔드 데이터의 방향은 모든 점수를 `높을수록 좋음`으로 통일하고, 사용자가 보는 화면에서는 부정 증상명이 그대로 점수처럼 보이지 않도록 문구를 조정하는 방식이다.

## 이 방향을 추천하는 이유

### 1. 구현 리스크가 가장 낮다

현재 백엔드와 AI 분석 흐름은 대체로 점수를 `높을수록 좋음`으로 해석하는 구조에 가깝다. 이 기준을 유지하면 저장된 데이터, 리포트, 비교 로직, 프론트 표시 방식 사이의 충돌을 줄일 수 있다.

반대로 `트러블/홍조는 낮을수록 좋고, 종합 점수는 높을수록 좋음`으로 바꾸면 지표별 방향이 섞인다. 이 경우 백엔드 분석 로직, AI 서버 프롬프트, 테스트, 문서, 프론트 문구를 모두 함께 맞춰야 해서 작업 범위가 커진다.

### 2. 남은 기간에 맞다

제출까지 약 2일 정도 남은 상황에서는 실제 연동 확인과 배포 안정성이 더 중요하다. 점수 체계를 크게 뒤집는 변경은 기능 자체보다 해석 오류를 만들 가능성이 크다.

### 3. 사용자에게도 충분히 직관적으로 만들 수 있다

원래 의도는 `홍조`, `트러블` 같은 문제성 지표는 낮을수록 좋고, 종합 점수는 높을수록 좋은 구조였다. 이 자체는 직관적이다.

다만 화면 문구를 아래처럼 바꾸면, 데이터 방향을 바꾸지 않고도 사용자 입장에서는 자연스럽게 이해할 수 있다.

- `트러블 점수` -> `트러블 안정도`
- `홍조 점수` -> `홍조 안정도`
- `수분 점수` -> `수분 컨디션`
- `피부 점수` 또는 `종합 점수` -> `오늘의 피부 컨디션`

이렇게 표현하면 모든 점수가 높을수록 좋은 값이어도 의미가 어색하지 않다.

## 백엔드에서 필요한 변경

1번 방향을 선택할 경우 백엔드 수정은 `점수 저장 구조 변경`이 아니라 **분석 해석 문구와 조건 정리**가 중심이다.

### 변경 대상

- 분석 변화량 해석
  - `delta > 0`은 개선
  - `delta < 0`은 악화

- 인사이트 문구
  - 점수가 오른 경우: 피부 상태가 좋아졌다는 표현
  - 점수가 내려간 경우: 피부 상태가 나빠졌다는 표현

- 홈 체크 로직
  - 트러블/홍조 점수가 낮으면 관리가 필요한 상태로 판단
  - 기존에 `높은 점수`를 문제 상태처럼 해석하는 코드가 있다면 `낮은 점수` 기준으로 수정

- AI 서버 프롬프트
  - 평균 변화량이 양수이면 개선
  - 평균 변화량이 음수이면 악화
  - 모델이 낮은 점수를 좋은 상태로 오해하지 않도록 문구 정리

- 테스트/문서
  - 지표 점수 방향을 `높을수록 좋음`으로 명시
  - 변화량 테스트의 기대 문구 수정

### 예상 수정 파일

- `backend/src/main/java/com/ildangbaek/backend/domain/analysis/service/LagCorrelationAnalyzer.java`
- `backend/src/main/java/com/ildangbaek/backend/api/analysis/service/LagInsightWriter.java`
- `backend/src/main/java/com/ildangbaek/backend/api/home/service/CheckHomeService.java`
- `ai-server/app/insight_tip.py`
- 관련 테스트 파일
- PRD/ERD/API 명세 또는 결정 문서

## 프론트에서 필요한 변경

프론트는 점수 값을 뒤집지 않고, **라벨과 설명 문구를 바꾸는 방향**이 좋다.

### 권장 문구

- `트러블` 단독 표기 대신 `트러블 안정도`
- `홍조` 단독 표기 대신 `홍조 안정도`
- `모공` 단독 표기 대신 `모공 컨디션`
- `수분` 단독 표기 대신 `수분 컨디션`
- `점수가 높을수록 좋은 상태`라는 전제를 화면 내부 문구 또는 디자인 가이드에서 통일

### 피해야 할 표현

- `트러블 80점`처럼 문제 자체가 높은 것처럼 보이는 표현
- `홍조 점수 상승`처럼 증상이 심해진 것인지 좋아진 것인지 헷갈리는 표현
- 개별 지표는 낮을수록 좋고 종합 점수는 높을수록 좋은 혼합 기준

## 디자인에서 결정해야 할 부분

디자인 파트에는 아래처럼 쉽게 설명하면 된다.

> 백엔드 점수는 모두 높을수록 좋은 상태로 통일하는 게 안전합니다. 그래서 화면에서는 `트러블 점수`라고 쓰기보다 `트러블 안정도`처럼 긍정 방향의 이름으로 보여주는 게 좋습니다. 그러면 사용자는 높은 점수를 좋은 상태로 자연스럽게 이해할 수 있고, 백엔드/AI/프론트도 같은 기준으로 동작합니다.

디자인에서 확정할 항목은 다음과 같다.

- 각 피부 지표의 최종 표시명
- 점수 색상 기준
  - 예: 낮음 = 주의, 중간 = 보통, 높음 = 좋음
- 변화량 표시 방식
  - 예: `+5`는 개선, `-3`은 악화
- 리포트 문구 톤
  - 예: `트러블이 늘었어요`보다 `트러블 안정도가 낮아졌어요`

## 이번 요청에서 바로 처리하지 않는 것이 좋은 부분

아래 방식은 더 직관적으로 보일 수 있지만, 지금 시점에서는 변경 범위가 크다.

- 트러블/홍조 같은 개별 문제 지표는 낮을수록 좋음
- 종합 점수는 높을수록 좋음

이 방식은 지표마다 방향이 달라져서 분석 로직, 리포트 문구, AI 서버, 프론트 그래프, 테스트를 모두 다시 맞춰야 한다. 제출 전 2일 내에 처리하기에는 실제 연동 중 예외가 생길 위험이 있다.

따라서 이번 제출 전에는 1번 방향으로 통일하고, 제출 이후 고도화 단계에서 지표별 방향성을 다시 설계하는 편이 안전하다.

## 회의에서 말할 내용 요약

- 현재 추천안은 `모든 점수는 높을수록 좋음`으로 통일하는 방식이다.
- 원래 의도였던 `트러블/홍조는 낮을수록 좋음`도 가능하지만, 백엔드/AI/프론트 변경 범위가 커진다.
- 남은 기간이 짧기 때문에 점수 체계는 유지하고, 화면 라벨을 `트러블 안정도`, `홍조 안정도`처럼 바꾸는 것이 가장 안전하다.
- 백엔드는 변화량 해석과 인사이트 문구가 이 기준과 맞는지 점검/수정한다.
- 프론트와 디자인은 라벨, 색상 기준, 증가/감소 표현을 같은 기준으로 맞추면 된다.
