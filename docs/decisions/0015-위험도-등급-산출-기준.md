# 0015. 위험도 등급 산출 기준 — 판정된 성분만 분모로 · 개수·비중 중 높은 쪽

- 상태: **제안**
- 날짜: 2026-08-12
- 담당: B
- 관련: F-CHECK-03, F-CHECK-04, ADR 0004 · 0009 · 0010 · 0011, CHECK-02 · CHECK-03

## 맥락

F-CHECK-03은 제품 전체 성분을 개인 성분 프로파일(F-ANALYSIS-04)과 대조해 위험도를 산출한다.
명세의 Business Rule은 방향만 정하고 수치는 정하지 않는다.

| BR | 내용 | 구현이 답해야 하는 것 |
| --- | --- | --- |
| 1 | 제품 전체 성분을 개인 프로파일과 비교한다 | — |
| 2 | `CAUTION` 성분의 수와 비중을 위험도 판단에 사용한다 | 수와 비중을 각각 어떻게 등급으로 바꾸는가 |
| 3 | `INSUFFICIENT` 성분은 위험도를 임의로 높이거나 낮추지 않는다 | 비중 계산의 분모에 무엇을 넣는가 |
| 4 | 개인 기록 근거가 있으면 성분별 사유를 함께 생성한다 | 근거가 없을 때 무엇을 채우는가 |
| 5 | 프로파일이 비어 있으면 위험도를 계산하지 않고 데이터 부족 상태를 반환한다 | "비어 있다"의 기준은 무엇인가 |

`docs/api_명세서.md` CHECK-02는 `CHECK_PROFILE_NOT_READY`(409)와 `CHECK_INGREDIENT_DATA_INSUFFICIENT`
(409) 두 코드를 명시하고, `RiskLevel` enum에는 `LOW`·`MEDIUM`·`HIGH` 외에 `INSUFFICIENT`도 정의돼
있다. 세 가지(등급 INSUFFICIENT 저장·PROFILE_NOT_READY·INGREDIENT_DATA_INSUFFICIENT)가 언제
각각 나오는지도 명세가 정하지 않는다.

**BR 2와 BR 3이 분모에서 충돌한다.** 가장 소박한 해석("CAUTION 수 / 전체 성분 수")으로 계산해 보면
왜 새 ADR이 필요한지 드러난다. CAUTION 2종·전체 5종인 제품은 비중 0.40이지만, 여기에 판정되지 않은
성분(INSUFFICIENT) 15종을 더해 전체 20종이 되면 비중이 0.10으로 떨어진다. **모르는 성분이 늘수록
위험도가 낮아지는 것**은 BR 3이 금지한 바로 그것이다 — INSUFFICIENT가 능동적으로 위험도를 "낮췄다."
분모를 무엇으로 두는가가 이 ADR의 핵심 결정이다.

ADR 0009(패턴 확정 3건·67%·3점)·0010(민감성 완화 2점)·0011(30일·20종)과 같은 성격의 미결정이며,
이 ADR이 F-CHECK 계열에서 같은 역할을 한다.

## 결정

### 1. 분모는 판정된 성분만이다

```
judged = suitableCount + cautionCount     // insufficientCount는 분모에서 뺀다
ratio  = cautionCount / judged
```

전체 성분 수가 아니라 **판정된 성분 수**(SUITABLE + CAUTION)만 분모로 쓴다. 이 분모에서는
INSUFFICIENT 성분을 아무리 더해도 `judged`와 `ratio`가 변하지 않는다 — BR 3이 근사가 아니라
항등식으로 성립한다.

### 2. 개수 축과 비중 축 중 더 심각한 쪽을 등급으로 삼는다

```
# 개수 축 (항상 적용)
cautionCount >= 3  → HIGH
cautionCount >= 1  → MEDIUM
cautionCount == 0  → LOW

# 비중 축 (judged >= 5일 때만 적용)
ratio >= 0.40      → HIGH
ratio >  0          → MEDIUM
ratio == 0          → LOW

riskLevel = 두 축 중 더 심각한 등급 (HIGH > MEDIUM > LOW)
riskScore = ratio * 100, 소수점 둘째 자리까지 반올림  // 게이트와 무관하게 항상 계산·저장
```

### 3. 비중 축에는 최소 판정 수 게이트(5종)를 둔다

판정 성분이 5종 미만이면 비중 축을 적용하지 않고 개수 축만으로 등급을 매긴다.

### 4. CAUTION이 하나라도 있으면 LOW가 아니다

개수 축의 최저 등급은 "CAUTION 0건"일 때만 LOW다. 1건이라도 있으면 최소 MEDIUM이다.

### 5. 두 409의 발동 조건과 검사 순서

| 코드 | 조건 |
| --- | --- |
| `CHECK_PRODUCT_NOT_FOUND` | 제품이 없거나 비활성(`active=false`) |
| `CHECK_INGREDIENT_DATA_INSUFFICIENT` | 제품의 `product_ingredients` 행이 0건 |
| `CHECK_PROFILE_NOT_READY` | `judged == 0` (이 제품의 성분 중 판정된 것이 하나도 없음) |

검사 순서는 제품 존재 → 성분 행 존재 → 판정 성분 존재다. 두 409 모두 **평가를 저장하지 않는다.**

### 6. `RiskLevel.INSUFFICIENT`는 저장하지 않는다

판정된 성분이 0건이면 등급을 매기지 않고 `CHECK_PROFILE_NOT_READY`를 던진다. `INSUFFICIENT`
상수는 ERD가 값으로 열거하므로 지우지 않되, 실제로 저장되는 경로는 없다.

### 7. 재분석은 새 행을 추가한다 (append-only)

같은 (사용자, 제품) 조합을 다시 분석해도 기존 행을 갱신하지 않고 새 `ProductRiskAssessment`를
쌓는다. `Idempotency-Key`는 명세에 "권장"으로 적혀 있으나 미구현(블로커 #8) 상태를 그대로 둔다.

### 8. 등급 문구는 `RiskLevel`에서 파생한다

| RiskLevel | title | description |
| --- | --- | --- |
| LOW | 잘 맞아요 | 내 피부 기준으로 주의할 성분이 없어요 |
| MEDIUM | 보통이에요 | 내 피부 기준으로 주의할 성분이 일부 있어요 |
| HIGH | 주의가 필요해요 | 내 피부 기준으로 맞지 않는 성분이 포함되어 있어요 |

`RiskLevel.title()` / `description()`이 유일한 산출 지점이다. `ProductRiskAssessment.summary`
컬럼에는 저장하지 않는다.

### 9. 근거 문구를 지어내지 않는다

`reason`은 `IngredientProfile.reasonSummary`에서 그대로 가져온다. 다음 두 경우 모두 `null`이다.

- 성분이 `INSUFFICIENT`(프로파일 행 자체가 없는 경우 포함)
- 성분이 `SUITABLE`/`CAUTION`인데 `reasonSummary`가 비어 있음

대체 문구를 만들지 않는다. 저장 시점과 조회 시점 모두 같은 규칙을 적용해 CHECK-02와 CHECK-03이
동일한 응답을 낸다.

### 10. 쓰지 않는 컬럼은 비운다

| 컬럼 | 값 |
| --- | --- |
| `risk_score` | `ratio * 100`, 소수점 둘째 자리 |
| `caution_count` / `suitable_count` / `insufficient_count` | 실제 개수 |
| `summary` | `null` |
| `contribution_score` | `null` |

`ProductRiskIngredient` 행은 INSUFFICIENT를 포함한 전 성분에 대해 남긴다.

## 근거

1. **분모가 BR 3을 항등식으로 만든다.** 맥락에서 든 산술(2/5=0.40 → 2/20=0.10)이 이 결정의
   전부다. 판정 분모에서는 INSUFFICIENT를 더해도 두 축이 불변이므로, "판단하지 않는다"가 코드
   구조로 보장된다.
2. **두 축이 서로의 실패 모드를 막는다.** 개수 축만 쓰면 판정 20종 중 CAUTION 12종(0.60)이
   HIGH를 못 넘는 구간이 생기고, 비중 축만 쓰면 40종짜리 제품의 CAUTION 12종(0.30)이 MEDIUM에
   머문다. 어느 한쪽만으로는 BR 2("수와 비중")를 충족하지 못한다.
3. **심각도 최대를 택한 이유.** ADR 0010 근거 3의 비대칭 비용을 그대로 승계한다 — 잘못된 HIGH는
   제품 하나를 안 사게 하지만, 잘못된 LOW는 맞지 않는 제품을 **사게** 만든다. 두 오판의 비용이
   다르므로 평균이 아니라 더 안전한 쪽(더 심각한 등급)을 택한다.
4. **비중 축에 게이트를 둔 이유.** 게이트가 없으면 CAUTION 1건·judged 2건만으로 ratio 0.50 →
   HIGH가 된다. 프로파일이 희소한 서비스 초기에는 제품당 판정 성분이 1~3종인 경우가 흔해,
   게이트 없이는 사실상 모든 결과가 HIGH로 붕괴한다. 표본이 작을 때 비율을 신뢰하지 않는다는
   판단은 ADR 0009가 "관측 3건 미만은 확정하지 않는다"로 이미 채택한 것과 같은 성격이다.
5. **LOW를 "CAUTION 0건"으로 좁힌 이유.** CAUTION은 ADR 0010 기준(관측 3건·일치 67%·변화량
   3점)으로 이미 확정된 악화 패턴이다. 그 위에 "잘 맞아요"라고 쓰는 것은 확정된 근거를 부정하는
   것과 같다.
6. **409를 택하고 `RiskLevel.INSUFFICIENT` 저장을 버린 이유.** 두 상태는 동시에 답일 수 없다.
   409는 행을 남기지 않으므로 CHECK-03이 다시 읽을 `checkId`가 없다. 값과 오류가 동시에 성립할
   수 없어, 명세가 명시한 409를 택했다. "빨간 오류 UI를 쓰지 않는다"(F-CHECK-04)는 **클라이언트
   렌더링 결정**이지 2xx 응답의 근거가 아니다.
7. **`judged == 0`이지 "프로파일 테이블이 비었나"가 아닌 이유.** 확정 성분 20종을 가진 사용자도
   겹치지 않는 제품 앞에서는 근거가 0이다. "프로파일 테이블이 비었는가"만 검사하면 그 사용자에게
   근거 0으로 `LOW / 잘 맞아요`가 나가는데, 이는 F-CHECK-04 AC("데이터 부족을 안전 또는 위험으로
   임의 판단하지 않는다")를 정면으로 어긴다. 이 조건은 ratio의 분모가 0이 되는 지점과 정확히
   일치해, 계산기에 별도의 0-나눗셈 분기가 필요 없다.
8. **근거 문구를 지어내지 않는 이유.** ADR 0010은 확정 행에 근거 문구가 항상 있다고 보장하지
   않는다. "과거 반응 이력 있음" 같은 일반 문구는 근거처럼 보이지만 근거가 아니며, BR 4가
   요구하는 "개인 기록 근거"를 위조하는 것이다.
9. **재분석이 append-only인 이유.** `ProductRiskAssessment`에는 수정 메서드도, `(user_id,
   product_id)` 유니크 제약도 없다 — 이미 append-only로 설계돼 있다. 평가는 특정 시점의 판단
   스냅샷이고 프로파일은 기록이 쌓일수록 바뀌므로, 덮어쓰면 지난주에 사용자에게 보여준 판단이
   조용히 재작성된다.
10. **임계값 3건·0.40·5종에 이론적 근거는 없다.** ADR 0009의 3점, 0010의 2점, 0011의 30일·20종과
    같은 성격의 초기값이다. 이 ADR은 값이 아니라 **형태**(두 축 · 판정 분모 · 심각도 최대 ·
    표본 게이트)를 고정한다.

## 결과

- `RiskLevelCalculator`(`domain/check`)가 이 규칙을 구현한다. 임계값 3종(`MIN_CAUTION_FOR_HIGH`
  =3, `HIGH_CAUTION_RATIO`=0.40, `MIN_JUDGED_FOR_RATIO`=5)이 이 클래스 한 곳에 모여 있다.
- `RiskLevel.INSUFFICIENT`는 **정의돼 있으나 저장되지 않는다.** ERD 11장이 값으로 열거하고
  있으므로 enum과 문서에서 지우지 않되, 죽은 값임을 여기 남긴다.
- `CHECK_CALCULATION_FAILED`(500)는 **던지는 경로가 없다.** 위험도 계산은 정수 셋의 산술이라
  실패할 수 없고, 없는 실패를 위한 처리를 넣지 않는다(CLAUDE.md §2).
- `ProductRiskAssessment.summary` · `ProductRiskIngredient.contribution_score`는 **비워 둔다.**
  쓸 값이 없다. 컬럼은 가중 산식이 이 ADR을 대체할 때를 위해 남는다.
- **응답 `message`가 명세와 다르다.** 명세 CHECK-02는 `"분석이 완료되었어요."`를 예시로 들지만,
  공용 `SuccessCode`에는 엔드포인트별 문구가 없어 `"생성에 성공했습니다."`가 나간다. 문구 하나
  때문에 공용 envelope를 바꾸지 않고, 명세 예시 쪽을 고친다.
- **`INSUFFICIENT`가 절대다수인 상태가 당분간 정상이다.** ADR 0010·0011의 제약을 그대로
  상속한다 — 온보딩(F-ONBOARD-02)이 없어 민감성 완화가 꺼져 있고, 실사용 기록이 쌓이기 전이라
  확정 성분이 거의 없다. 즉 실사용 경로에서는 `CHECK_PROFILE_NOT_READY`가 기본 응답일 가능성이
  높다. 이것은 고장이 아니라 정직한 상태지만, 프론트가 이 409를 빈 상태로 렌더링하지 않으면
  화면이 오류투성이로 보인다. **S-22 구현 시 반드시 확인해야 한다.**
- 실서버 검증에서 기존 시드(사용자 9001, 레티놀·히알루론산 CAUTION 2종)는 `judged=2`로 게이트
  (5종) 미만이라 **MEDIUM**이 나온다 — CAUTION 2종을 최고 등급으로 부르지 않는 것은 게이트의
  의도된 결과다. 이 값이 지나치게 관대하다고 판단되면 조정 대상은 게이트(5종)가 아니라 개수 축
  임계값(3건)이다.
- **임계값 재검토 시점** — ADR 0009와 같이 실기록이 2주 이상 쌓인 뒤. 세 ADR(0009·0010·0015)의
  수치는 독립이 아니다. 0009/0010이 느슨해지면 CAUTION 성분 수가 늘어 0015의 3건 문턱이 자동으로
  더 잘 걸린다.
- CHECK-01(쇼핑 홈)은 제품 목록(A 담당)이 없어 여전히 미착수다. 이 ADR은 CHECK-02·03에만
  적용된다.
