# 0025. 제품 추천 AI 코멘트 — ai-server 배치 생성 + 실패 시 null 폴백

- 상태: **수락**
- 날짜: 2026-08-16
- 담당: B
- 관련: [ADR 0016](0016-쇼핑-홈-추천-매칭-기준.md) · [ADR 0022](0022-openai-비전-2단계-점수-확정.md) · F-CHECK-01 · CHECK-01

## 맥락

CHECK-01 쇼핑 홈 추천(`CheckHomeService`)은 GOOD 성분 매칭이라는 규칙 기반 로직만으로
동작하고, `reason` 필드는 `"{성분명1}·{성분명2}이 잘 맞는 성분이에요"` 형태로 기계적으로
조립된 문자열이다(ADR 0016). 이 문구를 AI가 다듬은 자연스러운 한 줄 코멘트로 보완하고
싶다는 요구가 있었다.

ai-server는 이미 OpenAI 연동(`app/vision.py`)을 갖고 있고, 실패 시 폴백하는 패턴(ADR 0022)도
확립돼 있다. 제품 추천 자체의 판단 로직(무엇을 추천할지, 어떤 순서로 보여줄지)은 바꾸지 않고,
그 결과에 코멘트만 덧붙이는 것이 목표다.

## 결정

**AI 코멘트 생성을 ai-server의 신규 엔드포인트(`POST /product-comments`)로 위임하고, 추천
목록 전체를 한 번의 배치 프롬프트로 보낸다. 생성 실패는 추천 응답을 막지 않는다.**

```
CheckHomeService.buildRecommendations()
  규칙 기반으로 추천 목록(reason 포함) 조립
    → ProductCommentClient.generateComments(전체 목록)   ai-server 1회 호출
         ├ 성공 → productId별 aiComment 채움
         └ 실패/타임아웃 → 빈 맵 반환, 모든 aiComment는 null
```

세부 설계:

- **호출 위치**: ai-server(`app/product_comment.py`)에 신설. Spring은 OpenAI를 직접 호출하지
  않는다 — ADR 0022가 정한 "OpenAI는 ai-server 안에서만" 원칙을 그대로 따른다.
- **호출 횟수**: 제품 수만큼 개별 호출하면 지연·비용이 N배가 되므로, 추천 목록 전체를 한 번의
  OpenAI 호출로 묶는 배치 프롬프트를 쓴다(`response_format: json_object`로 구조화 출력).
- **실패 처리**: `ProductCommentClient`(Spring)는 ai-server 호출 실패를 예외로 전파하지 않고
  빈 맵으로 흡수한다. ai-server(`/product-comments`)도 OpenAI 실패 시 502로 응답하되, Spring이
  이를 `RestClientException`으로 잡아 폴백한다. 추천 자체는 AI 없이도 성립하는 핵심 기능이므로,
  AI 코멘트 실패가 추천 응답 전체를 막아서는 안 된다 — `LocalVisionSkinAnalysisClient`가
  분석 실패를 예외로 전파하는 것과는 의도적으로 다른 정책이다.
- **필드**: `CheckRecommendationResponse`에 `aiComment`(nullable)를 신규 추가한다. 기존
  `reason`은 그대로 유지한다 — `reason`은 근거 없는 추천을 만들지 않는다는 BR 2의 감사 대상이고,
  `aiComment`는 그 근거를 자연스럽게 다듬은 부가 정보일 뿐이다.

## 근거

1. **기존 실패 폴백 패턴(ADR 0022)을 재사용한다.** ai-server가 이미 "OpenAI 실패 시 조용히
   폴백"을 구현해 둔 자리가 있어, 같은 원칙을 코멘트 생성에도 그대로 적용할 수 있다.
2. **배치 프롬프트로 호출 비용을 고정한다.** 추천 제품 수가 늘어나도 ai-server 호출은 항상
   1회다.
3. **AI는 부가 기능으로 격리된다.** `aiComment`가 nullable이라 프런트엔드는 AI 코멘트가 없는
   경우를 이미 다뤄야 하는 구조가 되고, 이는 AI 의존도를 낮게 유지하려는 프로젝트 방향과
   맞는다.

## 대안 검토

- **제품별 개별 호출(병렬/순차)**: 기각. 추천 제품 수가 늘어날수록 호출 횟수·비용이 비례해서
  늘어난다. 배치 프롬프트는 호출 횟수를 1회로 고정한다.
- **코멘트를 미리 생성해 캐싱**: 기각(현재는). 제품-매칭성분 조합별 캐시 테이블이 필요해
  구현 복잡도가 늘어난다. 실시간 배치 호출로 우선 단순하게 시작하고, 지연·비용이 실사용에서
  문제가 되면 캐싱을 재검토한다.
- **`reason`을 AI 생성 문장으로 완전히 대체**: 기각. `reason`은 BR 2(근거 없는 추천 금지)의
  감사 대상이라 기계적으로 재현 가능한 문자열이어야 한다. AI가 생성한 문장으로 대체하면 그
  근거 추적이 어려워진다.
- **Spring에서 직접 OpenAI 호출**: 기각. ADR 0022가 "OpenAI 연동은 ai-server 안에서만"으로
  정리한 구조를 다시 두 갈래로 쪼갠다.

## 알려진 한계 (의도적으로 받아들인 트레이드오프)

- 매 홈 화면 요청마다 OpenAI를 호출하므로 캐싱 없이는 요청마다 지연·비용이 발생한다. 추천
  제품 수가 크게 늘어나면 배치 프롬프트 하나의 토큰 수도 함께 늘어난다.
- `aiComment`가 자주 `null`이 되는 상황(OpenAI 장애 지속 등)을 프런트엔드가 사용자에게 어떻게
  보여줄지는 이 ADR의 범위 밖이다.

## 결과

- `ai-server/app/schema.py`에 `ProductCommentRequest`/`ProductCommentBatchRequest`/
  `ProductComment`/`ProductCommentBatchResponse` 추가.
- `ai-server/app/product_comment.py` 신설 — `vision.py`와 같은 OpenAI 클라이언트 패턴.
- `ai-server/app/main.py`에 `POST /product-comments` 추가, 실패 시 502 + `COMMENT_UNAVAILABLE`.
- `backend`에 `ProductCommentClient`(`domain/product/client`) 신설 — 기존
  `LOCAL_VISION_BASE_URL`을 그대로 재사용해 같은 ai-server를 가리킨다. 실패는 빈 맵으로 흡수.
- `CheckRecommendationResponse`에 `aiComment`(nullable) 필드 추가.
- `CheckHomeService.buildRecommendations()`가 추천 목록 조립 후 배치로 코멘트를 요청하도록
  변경.
