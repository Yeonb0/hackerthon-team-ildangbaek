# 0017. 임시 인증 통합 — `X-User-Id` → 목업 Bearer 토큰

- 상태: **수락** ⚠️ 여전히 한시적 결정 · 배포 전 반드시 교체
- 날짜: 2026-08-13
- 담당: B
- 관련: [ADR 0006](0006-임시-인증-방편.md), AUTH-01~03·ONBOARD-01~05(A 담당), STATUS.md 2.3절

## 맥락

A가 `origin/jiwoo` 브랜치에서 AUTH-01~03(로그인·재발급·로그아웃)과 ONBOARD-01~05(온보딩)를
구현해 이 브랜치에 병합했다. 이 구현은 로그인 시 `mock-access-{userId}-{uuid}` 형식의 목업
Bearer 토큰을 발급하고, `Authorization` 헤더를 자체 리졸버(`CurrentUserResolver`)로 검증한다.

한편 SKIN·REPORT·CHECK·PRODUCT·USER 등 B 담당 도메인은 ADR 0006이 도입한
`CurrentUserIdArgumentResolver`로 `X-User-Id` 헤더를 그대로 신뢰하고 있었다. **두 메커니즘이
서로 다른 헤더·다른 리졸버를 쓰다 보니, 로그인으로 받은 토큰이 나머지 API에서 통하지 않았다.**
로그인 → 온보딩 → 분석 흐름을 하나로 잇는 데 실제 블로커였다.

## 결정

**`CurrentUserIdArgumentResolver`가 `X-User-Id` 대신 A가 이미 발급 중인 목업 Bearer 토큰
(`Authorization: Bearer mock-access-{userId}-{uuid}`)을 읽도록 바꾼다.** 토큰 파싱 로직은
`global/auth/MockAccessToken`으로 뽑아 `CurrentUserIdArgumentResolver`와 `CurrentUserResolver`
(auth/onboard가 쓰는 리졸버)가 함께 쓴다.

- 위치: `global/auth/MockAccessToken`(신규 공용 파서) · `global/auth/CurrentUserIdArgumentResolver`(수정)
  · `api/auth/service/CurrentUserResolver`(수정, 파싱만 위임)
- 헤더가 없거나 `Bearer` 접두어가 아니거나 목업 토큰 형식이 아니면 `401 COMMON_UNAUTHORIZED`
  (기존 ADR 0006과 동일한 에러코드 유지)
- 컨트롤러·서비스 시그니처는 전혀 바뀌지 않는다 — ADR 0006이 의도한 대로 리졸버 내부만 교체됐다.

## 근거

1. **ADR 0006이 예견한 전환이다.** "인증이 붙으면 리졸버 내부만 토큰 검증으로 바꾸면 되고,
   컨트롤러와 서비스는 건드리지 않는다"는 원래 설계 그대로 동작했다.
2. **두 파서를 따로 두지 않는다.** `CurrentUserResolver`가 갖고 있던 파싱 로직과 완전히
   동일했으므로(둘 다 `mock-access-{userId}-{uuid}` 파싱), `MockAccessToken`으로 합쳐 중복을
   없앴다.
3. **여전히 인증이 아니다.** 목업 토큰은 서명 검증이 없어 `mock-access-2-x`를 직접 보내면 2번
   사용자로 행세할 수 있다. `X-User-Id` 위조와 위험 수준이 같다 — 이번 변경은 "두 임시방편을
   하나로 합친 것"이지 "인증을 도입한 것"이 아니다.

## 실서버 검증 (2026-08-13)

로컬 MySQL + `bootRun`으로 로그인 → 온보딩 → 기존 B 도메인 API를 같은 토큰으로 이어서 호출했다.

| 단계 | 결과 |
| --- | --- |
| `POST /auth/login` | 201 · `mock-access-9301-...` 토큰 발급 |
| `GET /users/me/onboarding` (A 도메인) | 200 · 같은 토큰으로 상태 조회 |
| `GET /users/me` (B 도메인, USER-01) | 이전엔 `X-User-Id` 필요 · **같은 토큰으로 통과** — `UserProfile` 없어 `USER_NOT_FOUND`(정상) |
| `PATCH /users/me/onboarding/basic-info` → `GET /users/me` | 같은 토큰으로 마이페이지에 반영됨 확인 |
| `PATCH /users/me/onboarding/skin-types` (`SENSITIVE`) → `GET /users/me/ingredient-profile` (B 도메인, USER-02) | 같은 토큰으로 통과 · `user_skin_types` 행 생성 확인 |
| 토큰 없이 `GET /users/me` | 401 `COMMON_UNAUTHORIZED` |

전체 백엔드 테스트 199개 통과(기존 `X-User-Id` 하드코딩 테스트였던
`CurrentUserIdArgumentResolverTest`를 Bearer 토큰 형식으로 갱신).

## ⚠️ 보안 위험 — 배포 전 필수 교체 (ADR 0006과 동일)

**여전히 인증이 아니다.** 토큰 형식만 지키면 서명 없이 임의 사용자로 행세할 수 있다. 로컬 개발과
내부 시연에 한정하며, 실제 인증(JWT 서명 검증 등)이 도입되는 즉시 `MockAccessToken`과 두 리졸버
내부만 교체한다.

## 결과

- 로그인부터 분석 흐름(F-ANALYSIS 등)까지 프론트가 토큰 하나로 이어서 호출할 수 있다.
- 교체 시 변경 범위는 `MockAccessToken` 내부와 두 리졸버로 한정된다.
- `ErrorCode.AUTH_INVALID_TOKEN`은 `AuthService.refresh`(refresh 토큰 파싱 실패)에만 남는다 —
  `CurrentUserIdArgumentResolver`·`CurrentUserResolver`는 공통 규약을 따라 `COMMON_UNAUTHORIZED`로
  통일했다.
