# 0003. AI 피부 분석 — 인터페이스 + 목업 우선

- 상태: **수락**
- 날짜: 2026-08-08
- 담당: B(윤진)
- 관련: F-SKIN-04, `docs/api_명세서.md` 16장 External API Integration, SKIN-01

## 맥락

피부 분석은 외부 AI 서버에 의존한다. 그러나 착수 시점에 다음이 확정되지 않았다.

- 어떤 모델·서비스를 쓸지
- 요청/응답 스키마
- 사용 가능 여부와 응답 지연

이 의존성이 해결될 때까지 기다리면 **SKIN-01에 걸린 후속 작업 전체(분석 파이프라인 → 성분 프로파일 →
구매 전 위험도 → 리포트)가 멈춘다.** 이들은 모두 피부 기록 데이터를 입력으로 삼는다.

한편 `AnalysisMethod` enum은 이미 `AI` · `API` · `MOCK` 세 값을 가지고 있어, 분석 수단이 교체 가능하다는
전제가 스키마에 반영되어 있다.

## 결정

**분석 호출을 인터페이스로 추상화하고, 목업 구현을 먼저 만든다.**

```
SkinAnalysisClient (interface)
├── MockSkinAnalysisClient   ← 1순위. 결정적(deterministic) 점수 생성
└── (이후) 실제 구현체        ← 인터페이스만 만족하면 교체 가능
```

- 활성 구현체는 설정으로 전환한다 (`skin.analysis.provider=mock` 등).
- 저장 시 `SkinRecord.analysisMethod`에 실제 사용한 수단을 기록한다. 목업으로 만든 기록은 `MOCK`으로 남아
  **나중에 실데이터와 구분할 수 있다.**

## 근거

1. **후속 작업의 블로커를 제거한다.** 분석 파이프라인·위험도·리포트는 "피부 점수가 존재한다"만 필요하지,
   그 점수가 어디서 왔는지는 필요로 하지 않는다.
2. **목업이 실연동보다 테스트에 유리하다.** 분석 파이프라인 검증(성분 사용 → N일 후 점수 변화 → 반복성 판정)에는
   **의도한 패턴을 가진 결정적 입력**이 필요하다. 실제 AI 응답은 이 목적에 오히려 부적합하다.
3. **실패 경로를 미리 구현할 수 있다.** `SKIN_ANALYSIS_FAILED` · `SKIN_ANALYSIS_TIMEOUT` ·
   `SKIN_FACE_NOT_DETECTED`는 이미 `ErrorCode`에 정의되어 있다. 목업이 이 상황들을 재현할 수 있어야 한다.

## 목업 구현 요건

단순 난수는 쓰지 않는다. 분석 파이프라인 검증이 불가능해지기 때문이다.

1. **결정적이어야 한다.** 같은 입력 → 같은 출력. 시드는 `userId + recordDate + timeSlot`에서 유도한다.
2. **실패 상황을 유발할 수 있어야 한다.** 얼굴 미검출·타임아웃·분석 실패를 개발용 플래그로 재현한다.
3. **점수 범위는 0~100 정수.** 지표 구성은 ADR 0002를 따른다.

## 결과

- SKIN-01은 외부 서버 없이 end-to-end로 동작한다.
- 실연동 시 변경 범위는 **구현체 1개 + 설정값**이며, 서비스·컨트롤러·DTO는 건드리지 않는다.
- 목업으로 생성된 기록은 `analysis_method = MOCK`으로 식별된다. 실연동 전환 시 이 데이터를 그대로 둘지
  정리할지는 **전환 시점에 판단한다.**
- 프론트엔드도 동일한 목업 우선 전략을 쓰고 있다 (`EXPO_PUBLIC_USE_MOCK`). 전략이 일관된다.
