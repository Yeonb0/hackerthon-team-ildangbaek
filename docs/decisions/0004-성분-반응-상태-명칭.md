# 0004. 성분 반응 상태 명칭 — DB `SUITABLE` / API `GOOD`

- 상태: **수락**
- 날짜: 2026-08-08
- 담당: B(윤진)
- 관련: F-ANALYSIS-04, F-CHECK-03, `docs/공통응답포맷_예외처리코드.md` 6.4, USER-02 · CHECK-02

## 맥락

성분 반응 상태의 "맞음"에 해당하는 값의 이름이 계층마다 다르다.

| 출처 | 값 |
| --- | --- |
| `ReactionType.java` (구현) · `docs/ERD.md` 9장 | `SUITABLE` · `CAUTION` · `INSUFFICIENT` |
| `docs/공통응답포맷_예외처리코드.md` 6.4 IngredientStatus | `GOOD` · `CAUTION` · `INSUFFICIENT` |
| `api_명세서.md` CHECK-02 · USER-02 응답 JSON | `GOOD` · `CAUTION` · `INSUFFICIENT` |
| `기능명세서.md` F-ANALYSIS-04 분류표 | `GOOD`(맞음) · `CAUTION`(주의) · `INSUFFICIENT`(데이터 부족) |

`ReactionType.java`의 주석도 이 차이를 인지하고 「확정 시 라벨을 맞춘다」고 적어두었다.

`CAUTION`과 `INSUFFICIENT`는 양쪽이 이미 일치하므로 **문제가 되는 값은 `SUITABLE` / `GOOD` 하나뿐이다.**

## 결정

**둘 다 유지하고 경계에서 변환한다.**

- **DB · 도메인 계층**: `ReactionType.SUITABLE` 그대로 유지
- **API 응답**: `"GOOD"`으로 내보낸다
- 변환은 **DTO 매핑 지점 한 곳**에서만 수행한다. 도메인 코드가 `GOOD`이라는 문자열을 알 필요는 없다.

## 근거

1. **양쪽 다 이미 확정된 정본이다.** `ReactionType`은 `ingredient_profiles`와 `product_risk_ingredients`
   두 테이블의 컬럼 값이고, `GOOD`은 공통 응답 포맷 문서와 API 명세 응답 JSON에 박혀 있다. 어느 한쪽을 고치면
   다른 쪽 정본 문서와 이미 작성된 프론트 연동 계약이 깨진다.
2. **변환 비용이 사실상 없다.** 값 3개짜리 enum 매핑이며 지점도 한 곳이다.
3. **DB 값과 표현 값을 분리하는 것은 정상적인 설계다.** 표현 계층의 라벨이 바뀌어도(예: "맞음" → "잘 맞아요")
   저장된 데이터는 영향받지 않는다. 실제로 F-CHECK-03의 `RiskLevel`도 `LOW`/`MEDIUM`/`HIGH` 값과
   "잘 맞아요"/"보통이에요"/"주의가 필요해요" 라벨을 분리해 다루고 있다.

## 결과

- `ReactionType.java`와 `ERD.md`는 **수정하지 않는다.**
- 이 변환은 다음 응답에 적용된다: CHECK-02 `ingredients[].status`, CHECK-03,
  USER-02 `ingredients[].status` 및 `status` 쿼리 파라미터.
- **USER-02의 `status` 쿼리 파라미터는 입력 방향에도 변환이 필요하다.** 클라이언트가 `?status=GOOD`을 보내면
  `SUITABLE`로 역변환해 조회한다. 변환을 양방향으로 구현한다.

## 주의

`ReactionType`은 `analysis` 패키지에 있으나 `check` 도메인도 그대로 사용한다. 변환 로직을 두 도메인에
중복 구현하지 않는다. **공용 매핑 한 곳을 두고 양쪽이 참조한다.**
