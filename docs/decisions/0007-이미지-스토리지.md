# 0007. 이미지 스토리지 — 인터페이스 + 로컬 저장 우선

- 상태: **수락**
- 날짜: 2026-08-08
- 담당: B
- 관련: STATUS.md 5장 블로커 #3, SKIN-01, F-SKIN-02

## 맥락

SKIN-01은 얼굴 사진을 받아 저장한다. `SkinRecord.image_url`은 `VARCHAR(500)`으로 **URL을 담도록**
설계되어 있으나, 그 URL을 무엇이 만들어 주는지가 정해지지 않았다. S3·GCS·로컬 어느 것도 결정된 바 없고
관련 의존성도 없다. STATUS.md는 이를 블로커 #3으로 기록하며 SKIN-01 착수 불가로 표시했다.

## 결정

**`ImageStorage` 인터페이스를 두고 로컬 디렉터리 구현을 먼저 만든다.**

```
ImageStorage (interface)
└── LocalImageStorage   ← 현재 유일한 구현
    (이후) S3ImageStorage 등으로 추가
```

- 위치: `global/storage/` — 특정 도메인에 속하지 않는다
- 저장 경로와 URL 접두사는 설정값 (`app.storage.local.*`)
- 저장 실패 시 `SKIN_IMAGE_UPLOAD_FAILED` (500)

**형식·크기 검증은 스토리지가 아니라 서비스 계층에 둔다.** 무엇을 유효한 이미지로 볼지는 저장 방식이
아니라 각 API의 업무 규칙이기 때문이다. `SKIN_IMAGE_INVALID_FORMAT` · `SKIN_IMAGE_TOO_LARGE`는
SKIN-01의 규칙이지 스토리지의 관심사가 아니다.

## 근거

1. **ADR 0003과 같은 전략이라 일관된다.** 분석 클라이언트도 "인터페이스 + 목업 우선"으로 갔다.
   외부 의존성이 미정일 때 인터페이스로 막고 진행하는 방식을 저장소 전반에서 반복한다.
2. **해커톤 환경에서 즉시 동작한다.** S3는 버킷 생성·자격증명·권한 설정이 선행되어야 하고, 팀원 각자의
   로컬 환경에도 자격증명을 배포해야 한다. 로컬 저장은 설정 없이 바로 돌아간다.
3. **교체 비용이 낮다.** 인터페이스가 메서드 하나(`upload`)뿐이라 구현체 추가가 간단하다.

## 파일명 규칙

**클라이언트가 보낸 파일명을 쓰지 않는다.** UUID로 새로 만들고, 확장자는 검증을 통과한
Content-Type에서만 유도한다.

- 경로 조작 방지 — `../../etc/passwd` 같은 이름이 그대로 경로에 들어가면 안 된다
- 파일명 충돌 방지 — 같은 이름의 업로드가 서로 덮어쓰지 않는다

## ⚠️ 로컬 저장의 한계

- **서버가 여러 대면 동작하지 않는다.** 업로드를 받은 인스턴스에만 파일이 있다.
- **재배포하면 사라진다.** 컨테이너 디스크는 영속적이지 않다.
- 정적 서빙 설정을 따로 하지 않으면 반환한 URL로 실제 조회는 되지 않는다.
  현재 응답에 `imageUrl`을 포함하지 않아 문제되지 않으나, S-18에서 사진을 다시 보여줘야 하면
  그 시점에 서빙 설정 또는 외부 스토리지 전환이 필요하다.

배포 시점에 외부 스토리지로 전환한다. 전환은 이 ADR을 대체하는 새 ADR로 기록한다.

## 결과

- SKIN-01이 외부 스토리지 없이 end-to-end로 동작한다.
- `spring.servlet.multipart.max-file-size`를 10MB로 올렸다. 기본값(1MB)이면 정상 사진도 튕긴다.
- 상한 초과 시 `MaxUploadSizeExceededException`이 500이 되던 것을 명세대로 422로 변환한다.
