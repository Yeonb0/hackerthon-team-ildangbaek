# 0029. 피부 상태 코멘트 — OpenAI Vision 확정 단계에서 함께 생성 + 실패 시 null 폴백

- 상태: **수락**
- 날짜: 2026-08-18
- 담당: B
- 관련: [ADR 0022](0022-openai-비전-2단계-점수-확정.md) · [ADR 0025](0025-제품-추천-AI-코멘트.md) · [ADR 0028](0028-요인-상세-관리-팁.md) · F-SKIN-04 · F-SKIN-05 · SKIN-01

## 맥락

S-18(오늘 피부 결과) 화면에 점수 4종과 증감 외에, 사용자가 바로 이해할 수 있는 한 줄짜리 피부
상태 코멘트를 보여줄 필요가 생겼다. 예: "트러블은 줄었지만 색소잡티가 도드라지니 미백 케어를
더해보세요."

이 코멘트는 ADR 0028의 관리 팁과 같은 성격이다 — **저장된 수치로 규칙을 만들어 낼 수 없는
순수 생성 텍스트**다. 다만 근거가 다르다. 관리 팁은 이미 확정된 인사이트(성분-지표 관계)를
문장으로 풀지만, 이 코멘트는 **얼굴 사진 자체를 봐야** 쓸 수 있다 — 점수 4종만으로는 "어디가
어떻게 보이는지"를 설명할 수 없다.

ai-server의 `vision.refine()`(ADR 0022)이 이미 매 분석마다 원본 사진을 OpenAI Vision에 보내
최종 점수를 확정하고 있다. 이 호출에 코멘트 생성을 얹으면 새 API 호출을 추가하지 않고도 사진을
본 근거로 코멘트를 쓸 수 있다.

## 결정

**코멘트 생성을 별도 호출로 만들지 않고, `vision.refine()`이 최종 점수와 함께 `skin_comment`도
받도록 확장한다.**

```
ai-server/app/vision.py refine()
  OpenAI Vision 호출 (이미지 + 1차 점수, temperature=0)
    → 성공: {"TROUBLE":.., "REDNESS":.., "PORES":.., "PIGMENTATION":.., "skin_comment":"..."}
         scores·skin_comment 모두 채움
    → 실패/타임아웃/비신뢰 응답: VisionUnavailableError
         → pipeline.py가 1차 규칙 기반 점수로 폴백, skin_comment는 애초에 없음(None)
```

세부 설계:

- **호출 위치**: 새 엔드포인트를 만들지 않는다. 기존 `/analyze` 요청·응답에 필드만 추가한다.
  ADR 0025·0028이 각각 새 엔드포인트(`/product-comments`, `/insight-tips`)를 만든 것과 다르다 —
  이 코멘트는 이미 존재하는 호출의 부산물로 얻을 수 있어 그럴 필요가 없다.
- **코멘트 작성 규칙을 시스템 프롬프트에 명시한다**: 40~70자 한글, 개선이 필요한 항목 1~2개
  중심, 긍정적이고 친근한 톤, "질환"·"치료"·"병"·"심각" 등 의료적 진단으로 읽히는 표현 금지.
  ADR 0028의 관리 팁 프롬프트가 의학적 표현을 제약한 것과 같은 이유 — 의료 자문으로 오인되면
  안 된다.
- **폴백은 `null`이다.** 규칙 기반 1차 단계는 사진을 보지 않으므로(CIELAB 통계만 씀) 코멘트를
  지어낼 근거가 없다. OpenAI 호출이 실패하면 `AnalysisResult.skin_comment`는 애초에 채워지지
  않는다 — ADR 0025·0028과 같은 폴백 철학("근거 없으면 지어내지 않는다").
- **목업 분석(`MockSkinAnalysisClient`)도 `null`이다.** 이미지 내용을 보지 않는 결정적 목업이라
  코멘트를 만들 근거가 원천적으로 없다(`SkinAnalysisResult.ofScoresOnly()`가 이미 다른 근거
  없는 필드들을 `null`/빈 값으로 두는 것과 동일).
- **저장 위치**: `SkinRecord`(기록 단위)에 `skin_comment` 컬럼을 추가한다. `SkinMetric`(지표
  단위)에 두지 않는다 — 코멘트는 지표 하나가 아니라 사진 전체를 보고 쓴 한 문장이라 기록
  단위가 맞다.
- **응답 필드**: `SkinRecordResponse`(SKIN-01·02·03·REPORT-04가 공유하는 구조)에 `skinComment`
  를 추가한다. `null`이면 화면이 코멘트 영역을 생략한다 — 오류가 아니다.

## 근거

1. **이미 있는 호출에 얹을 수 있어 비용·지연이 추가되지 않는다.** ADR 0025·0028은 새 호출이
   필요했지만(추천 목록·인사이트는 `/analyze`가 모르는 데이터), 이 코멘트는 `/analyze`가 이미
   들고 있는 이미지와 점수만으로 충분하다.
2. **사진을 직접 보고 쓴 코멘트가 점수만으로 쓴 것보다 근거가 낫다.** 점수 4종을 후처리로
   조합해 문장을 만드는 대안도 있었지만, 그러면 "왜 그런지"는 결국 점수 격차라는 숫자 해석에
   그친다. OpenAI가 사진을 보고 쓰면 실제로 도드라지는 부위를 반영할 수 있다.
3. **기존 폴백 철학(ADR 0022·0025·0028)을 재사용한다.** 새로운 실패 정책을 만들지 않는다.

## 대안 검토

- **점수 4종만으로 Spring이 규칙 기반 문장을 생성**: 기각. "가장 낮은 지표 1~2개를 템플릿에
  끼워 넣는" 방식은 가능하지만, 사진 근거가 없어 상투적인 문장이 되고 ADR 0028이 관리 팁에서
  이미 피한 문제(성분 일반 지식으로 방향을 지어내는 것과 유사한 근거 부족)를 반복한다.
- **별도 엔드포인트(`/skin-comments`)로 분리**: 기각. ADR 0025·0028과 달리 이 코멘트는 `/analyze`
  가 이미 가진 이미지·점수만 필요해 분리할 이유가 없다. 분리하면 이미지를 두 번 보내야 한다.
- **`SkinMetric`에 지표별 코멘트를 붙이기**: 기각. Figma·기능 요구가 "지표별" 코멘트가 아니라
  "기록 전체"에 대한 한 문장이다. 지표 4개마다 문장을 받으면 화면에 다 못 넣고, 프롬프트도
  4배로 호출해야 한다.

## 알려진 한계 (의도적으로 받아들인 트레이드오프)

- ADR 0022가 이미 남긴 한계(클램핑 없음·변동성)가 코멘트에도 적용된다. 같은 사진이라도 재분석
  시 코멘트 문구가 달라질 수 있다(`temperature=0`이라 점수는 안정적이지만 문장 표현은 매번
  다를 수 있다).
- 코멘트 프롬프트 준수도는 실 API 키로 검증하지 않았다 — ADR 0022·0028과 같은 미검증 항목이다.
- `SkinRecord.skin_comment`는 마이그레이션 도구 없이 `ddl-auto: update`로만 반영된다(이 저장소의
  기존 관행, `docs/STATUS.md` 참고) — 운영 DB에 수동 반영이 필요할 수 있다.

## 결과

- `ai-server/app/schema.py` — `AnalysisResult.skin_comment: str | None = None` 추가.
- `ai-server/app/vision.py` — 시스템 프롬프트에 코멘트 작성 규칙 추가, `_parse()`가
  `skin_comment`도 함께 반환, `refine()`이 이를 `AnalysisResult`에 채움.
- `backend`의 `SkinAnalysisResult`에 `skinComment` 필드 추가, `LocalVisionSkinAnalysisClient`가
  `skin_comment`를 파싱, `MockSkinAnalysisClient`는 `ofScoresOnly()`를 통해 계속 `null`.
- `SkinRecord`에 `skin_comment` 컬럼(VARCHAR(200), NULL) 추가, `completeAnalysis()`가 저장.
- `SkinRecordResponse`에 `skinComment` 추가.
