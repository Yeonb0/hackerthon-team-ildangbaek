# 0010. 성분 프로파일 분류 기준 — 악화 우선 · 민감성 변화량 완화

- 상태: **제안**
- 날짜: 2026-08-10
- 담당: B
- 관련: F-ANALYSIS-04, ADR 0004 · 0009, USER-02 · F-CHECK

## 맥락

F-ANALYSIS-04는 F-ANALYSIS-01의 패턴 후보를 `ingredient_profiles`의 성분별 반응 상태로 접는다.
명세의 Business Rule은 방향만 정하고 수치는 정하지 않는다.

| BR | 내용 | 구현이 답해야 하는 것 |
| --- | --- | --- |
| 1 | 충분한 데이터가 없는 성분을 임의로 맞음/주의로 판단하지 않는다 | "충분"의 경계는 어디인가 |
| 2 | 데이터가 누적될 때마다 상태를 재평가한다 | 행을 대체하는가 갱신하는가 |
| 3 | **온보딩 피부 타입을 초기 해석 기준으로 사용한다** | 분류를 바꾸는가, 문구만 바꾸는가 |

BR 3이 가장 모호하다. 문자 그대로 "피부 타입으로 성분 상태를 정한다"고 읽으면 BR 1과 정면으로
충돌한다 — 민감성이라는 이유로 관측 없는 성분을 `CAUTION`으로 부르는 것이 바로 임의 분류다.

한 성분이 지표마다 다른 방향으로 확정되는 경우도 명세가 다루지 않는다. 레티놀이 모공은 개선하고
트러블은 악화시키는 상황은 실제로 흔하다.

## 결정

### 1. 분류는 확정된 패턴에서만 나온다

| 조건 | 상태 |
| --- | --- |
| 확정된 **악화** 패턴이 하나라도 있다 | `CAUTION` |
| 확정된 패턴이 **개선**뿐이다 | `SUITABLE` |
| 확정된 패턴이 없다 | `INSUFFICIENT` |

확정 기준은 ADR 0009(관측 3건 · 일치 67% · 변화량 3점)를 그대로 쓴다. **악화가 개선을 이긴다.**

같은 지표에서 시차만 다른 확정 패턴은 **1건으로 접는다.** 분석기가 (성분, 지표, 시차) 조합마다 후보를
내므로 접지 않으면 현상 하나가 `negative_count`를 최대 7까지 부풀린다. 대표는 변화량이 가장 큰 시차다.
F-ANALYSIS-01이 인사이트를 지표당 하나로 줄이는 것과 같은 규칙이다.

### 2. 피부 타입은 민감성의 악화 변화량 기준만 완화한다

민감성(`SENSITIVE`)을 선택한 사용자에 한해, **악화 방향**의 평균 변화량 기준을 3점에서 **2점**으로
낮춘다. 관측 쌍 수(3건)와 일치 비율(67%)은 완화하지 않는다.

- 관측이 0건인 성분은 피부 타입과 무관하게 `INSUFFICIENT`다.
- 개선 방향은 완화하지 않는다.
- 완화로 확정된 행의 `reason_summary`에는 `민감성 피부 기준 ·` 접두어를 붙인다.

### 3. 노출된 성분은 확정되지 않아도 행을 남긴다

`INSUFFICIENT` 행에 `observation_count`(노출 일수)만 채우고 `reason_summary` · `profile_score` ·
`confidence_score`는 `null`로 둔다.

### 4. 행은 삭제하지 않고 갱신한다

`UNIQUE(user_id, ingredient_id)` 기준으로 기존 행을 찾아 덮어쓴다. 인사이트(F-ANALYSIS-01)가
매 회차 삭제 후 재삽입하는 것과 다르다.

## 근거

1. **BR 1이 BR 3보다 우선한다.** 근거 없는 판단을 하지 않는 것이 이 제품의 신뢰 기반이다. 피부 타입은
   3지선다 자기 보고이고, 그것만으로 특정 성분의 반응을 알 수 있다면 애초에 기록을 받을 이유가 없다.
   그래서 BR 3은 **관측이 이미 있는 성분의 판정 문턱을 조정하는 것**으로만 해석한다.
2. **완화 대상이 변화량인 이유.** 관측 쌍 수와 일치 비율은 "이 변화가 반복되는가"를 재는 값이라 피부
   타입과 무관하다. 반면 변화량은 "얼마나 크게 반응하는가"이고, 민감성 피부가 같은 자극에 더 작은 폭으로도
   유의하게 반응한다는 것이 완화의 근거다. 반복성을 완화하면 우연을 패턴으로 부르게 된다.
3. **개선 방향을 완화하지 않는 이유.** 두 방향의 오판 비용이 다르다. 잘못된 `CAUTION`은 사용자가 성분
   하나를 덜 쓰게 하지만, 잘못된 `SUITABLE`은 민감성 피부 사용자가 맞지 않는 제품을 **사게** 만든다.
   F-CHECK가 이 표를 추천 근거로 읽으므로 결과가 구매로 이어진다.
4. **악화 우선도 같은 이유다.** 한 성분이 지표마다 다르게 움직일 때 `SUITABLE`이라 부르면 확정된 악화
   패턴이 표시에서 사라진다. `positive_count`와 `negative_count`를 둘 다 저장하므로 정보는 남는다.
5. **부족 행을 남기는 이유.** USER-02 BR 2가 `recordCount`로 "왜 아직 데이터가 부족한지" 설명하라고
   요구하는데, 성분별 노출 횟수를 아는 곳이 이 표뿐이다. 근거 문구를 `null`로 두는 것은 USER-02 BR 1이
   그대로 요구한다.
6. **갱신하는 이유.** 삭제 후 재삽입하면 행 id가 매번 바뀐다. 인사이트는 회차마다 새로 만드는 문구라
   그래도 되지만, 프로파일은 F-CHECK가 참조하는 누적 상태다.

## 결과

- `IngredientProfileWriter`가 이 규칙을 구현한다. `IngredientLagAnalysisService`가 시차 분석 직후 호출한다.
- **완화 임계값 2점에도 이론적 근거는 없다.** ADR 0009의 3점과 마찬가지로 목업 데이터로 조정한 초기값이며,
  실사용 데이터가 쌓이면 두 값을 함께 재검토한다.
- API 응답에서 `SUITABLE`은 `GOOD`으로 변환된다. (ADR 0004)
- 제품 기록 저장 API(PRODUCT-05, A 담당)가 없어 실사용 경로에서는 노출이 0건이라 프로파일도 비어 있다.
  F-ANALYSIS-01과 같은 제약이다.
- **결정 2(민감성 완화)는 당분간 실사용 경로에서 동작하지 않는다.** `skin_types` 마스터가 비어 있고
  온보딩 API(F-ONBOARD-02, A 담당)가 없어 `user_skin_types`에 아무도 없다. 즉 지금은 모든 사용자가
  기본 기준으로 판정된다 — 완화가 없는 쪽이 보수적이므로 안전한 방향의 degrade이지만, 조용히
  그렇게 되면 "완화가 고장난 것"과 구분되지 않으므로 선택 이력이 없을 때 로그를 남긴다.
  **이 ADR을 수락하기 전에 온보딩 구현 일정과 함께 검토해야 한다.**
- 환경 요인(F-ANALYSIS-02)이 없으므로 자외선 영향이 성분 반응으로 잡힐 수 있다. 민감성 완화는 이
  오분류 가능성도 함께 키운다 — F-ANALYSIS-02 구현 시 이 임계값을 재검토 대상에 포함한다.
