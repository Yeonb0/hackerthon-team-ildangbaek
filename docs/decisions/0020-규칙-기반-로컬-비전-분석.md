# 0020. 규칙 기반 로컬 비전 분석 — OpenCV/MediaPipe 자체 서버

- 상태: **부분 대체됨**([ADR 0022](0022-openai-비전-2단계-점수-확정.md)가 "Mock/OpenAI/local-vision
  3자 병존" 전제를 대체 — 규칙 기반 1차 산출 자체는 유지)
- 날짜: 2026-08-14
- 담당: B
- 관련: [ADR 0003](0003-AI-분석-목업-우선.md) · [ADR 0002](0002-피부-지표-체계.md) · [ADR 0022](0022-openai-비전-2단계-점수-확정.md) · F-SKIN-04 · SKIN-01

## 맥락

ADR 0003이 `SkinAnalysisClient` 인터페이스로 분석 수단을 추상화해 두었고, 현재 활성 구현체는
목업(`MockSkinAnalysisClient`)이다. 실연동 후보로 두 갈래를 검토했다.

1. 외부 VLM(OpenAI gpt-4o Vision) — `OpenAiSkinAnalysisClient`로 이미 구현돼 있으나 실 API 키로
   E2E 검증된 적은 없고, 호출마다 과금이 발생한다.
2. 팀이 직접 운영하는 분석 파이프라인(MediaPipe + OpenCV, 필요 시 PyTorch) — 산출 근거를 직접
   통제할 수 있고 과금이 없다.

PyTorch 기반 딥러닝 모델로 트러블·홍조·모공·색소침착(ADR 0002의 지표 4종)을 직접 학습하는 안을
가장 먼저 검토했으나, **이 4종을 라벨링한 데이터셋이 존재하지 않고 직접 구축할 여력도 없다.**
공개된 피부 분석 모델은 여드름 검출(bounding box)이나 피부질환 분류 같은 인접 태스크용이라
이 4개 점수 체계와 그대로 맞지 않는다. 데이터 없이 모델을 학습시키는 것은 이번 범위에서
현실적으로 불가능하다.

## 결정

**딥러닝 모델 학습 대신 규칙 기반(rule-based) 영상처리로 점수를 산출하는 자체 FastAPI 서버를
둔다.** MediaPipe Face Landmarker로 얼굴을 검출·정렬하고, 랜드마크에서 유도한 피부 영역
마스크와 CIELAB 색공간 통계로 지표를 계산한다.

```
Spring Boot                          FastAPI (ai-server/)
  SkinRecordService
    └ SkinAnalysisClient
        └ LocalVisionSkinAnalysisClient ──HTTP──> POST /analyze
             (provider=local-vision)                ├ MediaPipe Face Landmarker (얼굴 검출·정렬)
                                                      ├ 피부 영역 마스킹(눈·눈썹·입술 제외)
                                                      ├ Shades of Gray 화이트밸런스 + 품질 게이트
                                                      └ CIELAB 기반 지표 4종 산출(규칙 기반)
```

기존 두 구현체(`MockSkinAnalysisClient`, `OpenAiSkinAnalysisClient`)는 그대로 둔다. 셋 다
`provider` 설정값으로 전환 가능하며 서비스·컨트롤러·DTO는 건드리지 않는다(ADR 0003의 전제
그대로 유지).

## 근거

1. **학습 데이터가 없는 상태에서 "PyTorch 모델"을 표방하는 것은 정직하지 않다.** 라벨 없이
   학습한 모델은 검증 불가능한 블랙박스가 되어, 오히려 규칙 기반보다 신뢰하기 어렵다. 규칙
   기반은 각 점수가 어떤 픽셀 통계에서 나왔는지 항상 설명 가능하다.
2. **절대 정확도가 아니라 개인 변화 추적이 목적이라는 점과 규칙 기반의 한계가 맞아떨어진다.**
   이 서비스의 핵심 기능(F-ANALYSIS-01, "성분 사용 후 N일 뒤 지표 변화 반복성")은 절대 점수보다
   **같은 사람의 상대적 변화 방향**이 맞는 것이 더 중요하다. 규칙 기반은 절대 정확도를 보장할 수
   없지만, 동일 파이프라인을 일관되게 적용하면 방향성은 충분히 잡아낼 수 있다(아래 실측 참고).
3. **비용·오프라인 동작.** 외부 API 호출·과금이 없고, 네트워크 장애의 영향을 받지 않는다.
4. **점진적 교체가 가능한 구조를 그대로 유지한다.** `metrics.py`의 점수 산출 함수 하나만
   나중에 모델 추론으로 바꾸면 되도록 파이프라인을 단계별로 분리했다(얼굴 검출 → 영역 분리 →
   전처리 → 지표 산출). 학습 데이터가 생기면 마지막 단계만 교체 대상이다.

## 알려진 한계 (의도적으로 받아들인 트레이드오프)

- **의학적 정확도를 보장하지 않는다.** 정답 라벨이 없어 절대 점수의 타당성을 검증할 방법이
  없다. 이 점수는 참고용이며, 사용자에게 의학적 진단으로 제시하면 안 된다.
- **점수 구간값(`metrics.py`의 `*_RANGE` 상수)은 근거 있는 데이터가 아니라 합성 이미지 실측으로
  잡은 초기값이다.** 실사용 데이터가 쌓이면 반드시 재조정해야 한다.
- **PORES(모공) 지표는 신뢰도가 낮다.** 실측(연속 촬영 5장, 센서 노이즈만 다름)에서 spread가
  8점까지 벌어졌다 — 카메라 노이즈·JPEG 압축 아티팩트와 모공 신호가 같은 고주파 대역에 있어
  원리적으로 완전히 분리되지 않는다. 반면 REDNESS·TROUBLE·PIGMENTATION은 같은 조건에서 spread
  0~1점으로 안정적이다(`ai-server/README.md`의 신뢰도 표 참고).
- **조명·화질에 여전히 민감하다.** Shades of Gray 화이트밸런스와 품질 게이트(초점·노출)로
  억제하지만 완전히 제거하지 못한다. 강한 백열등 조건에서 REDNESS가 최대 8점까지 흔들리는 것을
  실측했다.

## 대안 검토

- **BiSeNet 등 별도 세그멘테이션 모델 추가**: 검토했으나 채택하지 않았다. MediaPipe 랜드마크
  윤곽에서 눈·눈썹·입술을 빼는 것만으로 피부 영역 분리가 충분했고(실측으로 눈·입술 중심이
  마스크에서 정확히 제외됨을 확인), 200MB급 모델을 추가로 싣을 이유가 없었다.
- **피부 픽셀 기준 Gray World 화이트밸런스**: 처음에 시도했으나 기각했다. 피부 평균을 무채색으로
  맞추면 홍조 신호 자체가 지워진다(실측: 붉은 피부·창백한 피부 모두 a*가 0으로 수렴). 장면 전체를
  기준으로 조명만 추정하는 Shades of Gray로 바꿔 해결했다.
- **CLAHE(국소 명암 대비 정규화)를 전처리에 포함**: 기각했다. 국소 대비를 평탄화하는 연산이라
  색소침착(국소 편차)·모공(고주파 텍스처) 신호를 함께 지운다. 코드에는 남겨 두되(`normalize_luminance`)
  자동 파이프라인에서는 쓰지 않는다.

## 결과

- `provider=local-vision`으로 전환하면 이 구현체가 활성화된다. 저장되는 `SkinRecord.analysisMethod`는
  `API`다(외부 VLM의 `AI`, 목업의 `MOCK`과 구분).
- `ai-server/` 하위에 FastAPI 서버를 신설했다. 실행·테스트 방법은 `ai-server/README.md` 참고.
- 얼굴 랜드마크 모델(`face_landmarker.task`, 3.7MB)은 저장소에 포함하지 않고 `scripts/download_model.sh`로
  설치 시점에 받는다.
- 상태를 **제안**으로 둔다. 실사용 데이터로 점수 구간값을 재조정하고 실제 얼굴 사진으로 검증하기
  전까지는 팀 합의 전 단계로 취급한다.
