# 0016. 쇼핑 홈 추천 매칭 기준 — GOOD 성분 · key_ingredient · 제품 단위 dedup

- 상태: **제안**
- 날짜: 2026-08-13
- 담당: B
- 관련: F-CHECK-01, ADR 0004 · 0010 · 0011, CHECK-01

## 맥락

F-CHECK-01(쇼핑 홈)은 "추천은 개인 성분 프로파일을 근거로 하며, 근거 없는 추천은 노출하지
않는다"(BR 2)만 정하고 구체적 매칭 규칙은 정하지 않는다. `docs/api_명세서.md` CHECK-01 절의
응답 예시에는 `reason`이 `"판테놀·마데카소사이드가 잘 맞는 성분이에요"` 형태로 나오지만, 이 문구를
어떻게 조립하는지는 명세가 정하지 않는다.

F-ANALYSIS-05(프로파일 완성도)의 세 소비처(USER-01·USER-02·CHECK-01) 중 CHECK-01만 미구현이라
BR 4(값 일치)를 검증할 수 없던 상태를 해소하는 작업에서, CHECK-01을 구현하려면 이 매칭 규칙을
먼저 정해야 했다.

## 결정

### 1. 추천 후보는 GOOD 성분을 핵심 성분으로 가진 제품이다

```
goodIngredientIds = ingredient_profiles에서 reaction_type = SUITABLE인 성분 ID
candidates = product_ingredients에서 ingredient_id in goodIngredientIds
             and key_ingredient = true
             and product.active = true
```

`CAUTION`·`INSUFFICIENT` 성분은 추천 근거로 쓰지 않는다. `key_ingredient = false`인 성분(제품에
포함돼 있지만 핵심 성분이 아닌 것)도 매칭에서 뺀다 — 근거로 내세우기엔 약한 연결이기 때문이다.

### 2. 제품 단위로 중복을 제거한다

한 제품이 여러 GOOD 성분을 핵심 성분으로 가져도 추천 목록엔 1건만 나온다. 매칭된 GOOD 성분명을
모두 모아 `reason`을 조립한다.

```
reason = "{성분명1}·{성분명2}...이 잘 맞는 성분이에요"
```

### 3. GOOD 성분이 없으면 매칭 쿼리 자체를 실행하지 않는다

`goodIngredientIds`가 비어 있으면 `recommendations: []`를 즉시 반환한다(BR 2, 오류 아님).

### 4. `failedSections`는 항상 빈 배열이다

`docs/api_명세서.md` 1.8절의 `failedSections`는 BFF가 **외부 API**(날씨 등, HOME-01 사례) 부분
실패를 알리는 공용 필드다. CHECK-01의 추천 로직은 전부 내부 DB 조회이고 외부 API 호출이 없으므로
실패할 섹션이 구조적으로 없다.

## 근거

1. **`key_ingredient`로 좁힌 이유.** 제품에 포함된 성분 전체를 매칭에 쓰면, 미량 함유된 GOOD
   성분 하나로도 추천에 오를 수 있다. "잘 맞는 성분이에요"라는 문구가 실제로는 그 제품의 정체성과
   무관한 성분을 근거로 들 위험이 있어, 제품을 대표하는 성분(`key_ingredient = true`)만 근거로
   인정한다.
2. **CAUTION·INSUFFICIENT를 근거로 쓰지 않는 이유.** BR 2가 "근거 없는 추천은 노출하지 않는다"고
   정했고, ADR 0010·0015가 이미 CAUTION을 "확정된 악화"로, INSUFFICIENT를 "판단 불가"로 다루고
   있다 — 둘 다 추천의 근거가 될 수 없다.
3. **제품 단위 dedup이 필요한 이유.** 매칭을 성분 단위로 두면 같은 제품이 성분 수만큼 중복
   노출된다. 사용자에게는 "이 제품을 사라"는 판단 하나만 필요하고, 그 판단을 뒷받침하는 성분은
   여러 개일 수 있다.
4. **`failedSections`를 고정한 이유.** ADR 0011·0015와 마찬가지로 존재하지 않는 실패 케이스에
   대한 처리를 미리 만들지 않는다(CLAUDE.md §2). 외부 API가 이 화면에 붙는 시점에 다시 연다.
5. **임계값 없는 결정.** 이 ADR은 값(개수 제한, 순위 가중치 등)을 정하지 않는다 — 매칭
   **형태**만 고정한다. ADR 0009·0010·0011·0015와 같은 성격으로, 실사용 데이터가 쌓이면
   재검토 대상이다. 특히 추천 수가 지나치게 많거나 적을 때 상한·정렬 기준을 추가하는 것은
   이 ADR의 범위 밖이다.

## 결과

- `CheckHomeService`(`api/check/service`)가 이 규칙을 구현한다.
- `ProductIngredientRepository.findAllWithProductByIngredientIdInAndKeyIngredientTrue`(신규)가
  후보 조회를 담당하고, 제품 단위 그룹핑은 서비스 계층에서 처리한다.
- `profileCompletion`은 `ProfileCompletionCalculator`(ADR 0011)를 그대로 호출한다 — 이 ADR은
  완성도 산출식과 무관하다.
- 추천 순서·개수 상한은 정하지 않았다. 현재는 매칭된 전체를 반환한다.
