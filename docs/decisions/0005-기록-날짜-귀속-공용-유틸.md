# 0005. 기록 날짜 귀속 규칙의 공용 유틸화

- 상태: **확정** (2026-08-11, A 합의 완료 — 공용 유틸로 사용)
- 날짜: 2026-08-08
- 담당: B
- 관련: `docs/공통응답포맷_예외처리코드.md` 8.1, F-HOME-01, SKIN-01, PRODUCT-05

## 맥락

기록의 날짜 귀속 규칙은 이미 확정되어 있다 (공통 응답 포맷 8.1):

1. `NIGHT` 슬롯 기록은 **"밤이 시작된 날짜"로 귀속한다.** 18:00~23:59는 그날 날짜,
   자정을 넘겨 00:00~05:59에 기록해도 **전날 날짜**로 저장한다.
2. `MORNING` 슬롯은 기록 시각의 달력 날짜를 그대로 쓴다.
3. 낮/밤 판정은 클라이언트 기기 시간을 쓰되, **날짜 귀속은 서버 시간 기준**으로 계산한다.

문제는 **이 규칙을 A·B 양쪽이 모두 필요로 한다**는 점이다.

| 사용처 | 담당 |
| --- | --- |
| `POST /skin-records` — 슬롯 중복 판정, 전일 동일 시간대 비교 | **B** |
| `POST /product-records` — 슬롯 중복 판정 | **A** |
| `POST /routines/{id}/records` | **A** |
| 기록 허브 캘린더 · 슬롯 상태 조회 | **A** |

각자 구현하면 **두 벌의 날짜 계산 로직이 생기고, 미묘하게 어긋날 때 증상이 최악이다.** 같은 밤에 찍은
제품 기록과 피부 기록이 서로 다른 날짜로 저장되면 성분-피부 시차 분석(F-ANALYSIS-01)의 입력 자체가 깨진다.
공통 문서 8.1의 결정 배경도 정확히 이 어긋남을 막으려는 것이었다.

## 결정

**날짜 귀속 계산을 `global` 패키지의 공용 유틸 하나로 두고 A·B가 함께 사용한다.**

- 위치: `global/util/` — 특정 도메인에 속하지 않음을 명확히 한다
- 입력: 기록 시각(서버 시간) + `TimeSlot`
- 출력: 귀속 `LocalDate`
- **B가 먼저 구현하고 단위 테스트를 붙인다.** Step 1에서 피부 기록보다 먼저 필요하기 때문이다.
- A 담당은 제품 기록에서 이를 **그대로 호출한다.** 별도 구현하지 않는다.

## 근거

1. **규칙이 이미 확정되어 있어 해석의 여지가 없다.** 구현이 갈릴 이유가 없는데 두 벌을 두는 것은 순수한 위험이다.
2. **어긋났을 때 발견이 늦다.** 자정 전후 기록에서만 재현되고, 증상은 분석 결과가 조용히 부정확해지는 것이다.
3. **양쪽 도메인 어디에도 속하지 않는다.** `record` 패키지에 두면 소유권이 모호해진다. `global`이 적절하다.

## 검증 기준

경계값을 단위 테스트로 고정한다.

| 기록 시각 | 슬롯 | 귀속 날짜 |
| --- | --- | --- |
| 08:00 | `MORNING` | 당일 |
| 20:00 | `NIGHT` | 당일 |
| 23:59 | `NIGHT` | 당일 |
| 00:00 | `NIGHT` | **전날** |
| 05:59 | `NIGHT` | **전날** |

## 미해결

- **`MORNING` 슬롯을 06:00 이전이나 18:00 이후에 요청하면 어떻게 되는가.** 규칙 3에 따르면 슬롯은
  클라이언트가 정해서 보내므로 서버는 시각과 무관한 조합을 받을 수 있다. `RECORD_INVALID_TIME_SLOT`으로
  거절할지, 그대로 수용할지 정해지지 않았다. **A·B 공통 문제이므로 함께 결정한다.** (현재는 수용 —
  STATUS.md 미해결·블로커 #6)
- A 담당이 제품 기록(`product-records`)에서 이 유틸을 호출할 때 다른 방식이 필요해지면, **호출부가 아니라
  이 유틸을 고치는 것으로 대응한다.**
