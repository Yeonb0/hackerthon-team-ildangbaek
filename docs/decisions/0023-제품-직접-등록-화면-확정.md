# 0023. 제품 직접 등록 — ProductManualRegisterScreen을 정식 화면으로 확정

- 상태: **수락**
- 날짜: 2026-08-15
- 담당: B
- 관련: `docs/기능명세서.md` F-PRODUCT-08 「TBD-07」, `docs/api_명세서.md` PRODUCT-09 · PRODUCT-10

## 맥락

F-PRODUCT-08(제품 직접 등록)은 S-11 · S-12의 `제품 등록` / `직접 등록하기` 버튼이 갈 화면이
명세서에 정의되지 않은 채 "TBD-07 · 최우선"으로 남아 있었다. 그런데 프론트는 2026-08-13 관리자
결정으로 `ProductManualRegisterScreen`(`frontend/src/screens/product/ProductManualRegisterScreen.tsx`)을
이미 완성해 붙여뒀다 — 제품명 · 브랜드명 · 카테고리 탭 · 성분 자유 텍스트 입력 · 사진 촬영까지 구현돼
있고, 저장만 세션 한정 목업(`registerMockProduct`)으로 대신하고 있었다. 매칭 조회
(PRODUCT-09, `GET /products/match`)는 그 화면의 자동완성을 위해 먼저 백엔드에 구현돼 있었다.

즉 "화면이 없어서 명세를 확정할 수 없다"는 TBD-07의 전제가 이미 사실과 어긋나 있었다 — 화면은
있었고, 명세와 저장 API만 없었다.

## 결정

**`ProductManualRegisterScreen`을 F-PRODUCT-08의 정식 화면으로 확정한다.** 그 화면이 실제로
보내는 값(제품명 · 브랜드명 · 카테고리 · 자유 텍스트 성분 배열 · 선택적 사진)을 계약으로 삼아
`POST /api/v1/products`(PRODUCT-10)를 구현한다.

추가로 다음 세 가지를 확정한다.

1. **성분 처리**: 자유 텍스트로 입력한 성분명이 기존 `Ingredient` 카탈로그에 없으면 신규로
   생성해 연결한다. 화면 안내 문구가 "일부만 입력하거나 비워도 된다"고 명시하므로, 등록을
   막지 않고 최대한 그대로 살린다.
2. **노출 범위**: 등록된 제품(`dataSource=USER`)은 등록 즉시 `active=true`로 전체 공개되며
   다른 사용자에게도 검색 · 매칭 · 스캔 결과로 동일하게 노출된다. 등록자 전용 비공개 상태는
   이번 범위에 없다.
3. **중복 처리**: 서버는 이름 · 브랜드 중복을 막지 않는다. PRODUCT-09가 이미 등록 전 조회
   기능으로 존재하므로, 중복 안내는 클라이언트가 그 조회 결과를 사용자에게 보여주는 방식으로
   충분하다고 판단했다.

## 근거

1. **프론트 화면이 이미 실사용 가능한 완성도로 존재한다.** 새 화면을 기획 · 디자인하는 비용
   없이 바로 정본으로 채택할 수 있다. TBD-07이 요구한 "화면 추가 또는 버튼 제거" 중 화면 추가는
   사실상 끝나 있었다.
2. **성분 텍스트를 버리지 않는 편이 F-PRODUCT-04(성분 확인)와의 연계에 유리하다.** 신규
   등록된 제품도 다른 제품과 동일하게 `ProductIngredient`로 연결되어야 CHECK-01(성분 기반
   추천) · 성분 프로파일 분석의 입력 대상이 될 수 있다. 성분을 저장하지 않으면 사용자가 직접
   등록한 제품만 분석 사각지대에 남는다.
3. **전체 공개가 MVP 범위에서 더 단순하고, 실제 유스케이스와도 맞는다.** 직접 등록은 대부분
   "카탈로그에 없는 제품을 채워 넣는" 동기이므로, 다른 사용자도 검색해서 쓸 수 있는 편이
   카탈로그 확장에 부합한다. 소유자별 비공개를 지원하려면 `Product`에 소유자 컬럼을 추가하는
   스키마 변경이 필요한데, 이번 MVP 범위에서 정당화되지 않는 복잡도다.
4. **서버측 중복 차단은 명세에 근거가 없다.** `barcode`만 UNIQUE이고 `name`+`brand` 조합에는
   제약이 없다. PRODUCT-09가 이미 조회 수단을 제공하므로, 강제 차단보다 사용자 판단에 맡기는
   쪽이 스캔 실패 → 직접 등록이라는 폴백 흐름을 막지 않는다.

## 결과

- `POST /api/v1/products`(PRODUCT-10)가 신설된다. 스키마 변경은 없다 — `Product.dataSource`가
  이미 갖고 있던 `USER` 값을 실제로 세팅하는 코드 경로가 이번에 처음 생겼을 뿐이다.
- `IngredientRepository`에 `findByKoreanName`이 추가됐다(신규 성분 중복 생성 방지용).
- 이미지 업로드는 `SkinRecordController`와 동일하게 `multipart/form-data` + 기존
  `ImageStorage`(`LocalImageStorage`)를 재사용한다.
- **이번 범위에서 제외한 것**(후속 필요 시 별도 ADR로 다룬다):
  - 소유자별 비공개(`Product`에 등록자 컬럼 추가) — 전체 공개로 대신한다.
  - 서버측 이름 · 브랜드 중복 차단(UNIQUE 제약 등).
  - 화면 안내 문구에 언급된 "AI가 바코드 · 사진으로 성분을 채워주는" 자동완성 — 프론트
    주석에도 명시돼 있듯 실제 기능이 아니다.
  - PRODUCT-09 매칭 조회와 `ProductManualRegisterScreen`의 자동완성 연동 — 프론트가 아직
    호출하지 않고 있으며, 이번 백엔드 작업과 독립적인 별도 프론트 작업이다.
  - 프론트 `RegisterProductInput` 타입에 `imageUri` 필드가 빠진 기존 불일치, `registerProduct()`의
    `USE_MOCK` 미분기 — 이번 작업은 백엔드만 다뤘으므로 프론트 연동은 후속 작업으로 남는다.
