# 0001. 피부 기록 저장 시점 — 분석 완료 시 저장

- 상태: **수락**
- 날짜: 2026-08-08
- 담당: B
- 관련: `docs/api_명세서.md` SKIN-01 「⚠ 저장 시점 · TBD-10b」, F-SKIN-03 · F-SKIN-04 · F-SKIN-05

## 맥락

화면 흐름(S-16 촬영 → S-17 분석 중 → S-18 결과)에서 피부 기록의 저장 지점이 명확하지 않았다.
화면 구조만 보면 S-18의 `확인` 버튼이 저장 지점처럼 읽히는데, 그대로 구현하면 **사용자가 확인을 누르지 않고
이탈할 때 분석 결과가 유실된다.** 이미 AI 분석 비용을 치른 뒤이므로 유실은 사용자와 서버 양쪽에 손해다.

`api_명세서.md`는 두 안을 제시하고 A안을 전제로 작성되어 있으나, 「구현 착수 전 확정이 필요합니다」라고
명시적으로 열어둔 상태였다.

| 안 | API 구조 | 성격 |
| --- | --- | --- |
| A. 분석 완료 시 저장 | `POST /skin-records` 1회 | 유실 없음 · 사용자가 취소해도 기록이 남음 |
| B. 확인 시 저장 | `POST /skin-records/analyze` → `POST /skin-records` | 사용자 의도 존중 · 유실 위험 · 이미지 임시 보관 필요 |

## 결정

**A안을 채택한다.** `POST /api/v1/skin-records` 한 번의 호출로 업로드 · 분석 · 저장이 모두 끝난다.
S-18의 `확인` 버튼은 **화면을 닫는 역할만** 하며 서버 호출을 발생시키지 않는다.

## 근거

1. **분석 결과 유실이 가장 큰 손실이다.** 피부 기록은 하루 최대 2건뿐이고, 이 데이터가 개인 성분
   프로파일(F-ANALYSIS-04)과 리포트(F-REPORT-01)의 유일한 입력이다. 한 건의 유실이 분석 품질에 직접 영향을 준다.
2. **B안은 이미지 임시 보관 계층을 추가로 요구한다.** 분석과 저장 사이에 이미지를 어디에 얼마나 들고 있을지,
   확인하지 않은 이미지를 언제 정리할지에 대한 정책과 배치가 필요하다. MVP 범위에서 정당화되지 않는 복잡도다.
3. **하루 1슬롯 1건 제약과 잘 맞는다.** `skin_records`는 `(user_id, record_date, time_period)` 유니크 제약을
   가지므로, 저장이 곧 슬롯 점유다. 저장 시점이 둘로 나뉘면 중복 판정(`SKIN_ALREADY_RECORDED_IN_SLOT`) 시점도
   함께 흔들린다.

## 결과

- API는 SKIN-01 하나로 유지된다. `POST /skin-records/analyze`는 만들지 않는다.
- 사용자가 결과를 보지 않고 이탈해도 기록은 남는다. **이는 의도된 동작이다.**
  기록 취소·삭제 기능은 이번 MVP 범위 밖이며, 필요해지면 별도 ADR로 다룬다.
- 트랜잭션 경계는 `api_명세서.md` 15장의 권고를 따른다 — 외부 호출(업로드·AI)은 트랜잭션 **밖**,
  DB 반영만 트랜잭션 안:

  ```
  [TX 밖] 이미지 업로드 → AI 분석 호출
  [BEGIN] SkinRecord INSERT → SkinMetric INSERT → 환경 연결 → IngredientProfile UPDATE [COMMIT]
  ```

- 분석이 실패하면 `SkinRecord.failAnalysis()`로 `analysis_status = FAILED`를 남긴다.
