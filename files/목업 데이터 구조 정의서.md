# 목업 데이터 구조 정의서

> 작성 기준: ERD v1 + API 명세서 v1.0
목적: 백엔드 완성 전 프론트엔드 개발용 목업 데이터의 구조를 정의하고, 실제 연동 시 오류가 발생하지 않도록 응답 형태를 명세서와 1:1로 맞춘다.
> 

---

## 1. 설계 원칙

| # | 원칙 | 근거 |
| --- | --- | --- |
| 1 | 목업 구조의 기준은 **ERD 컬럼명이 아니라 API 응답 필드명** | ERD `brand_name` → API 응답은 `brand`. 화면은 API만 바라봄 |
| 2 | 모든 응답은 공통 봉투 `{isSuccess, code, message, result}`로 감싼다 | 명세서 §7 Response 규칙 |
| 3 | 모든 ID는 숫자(number) | 명세서 §11 — 백엔드 Long → JSON number |
| 4 | Enum은 문자열로만 사용 (숫자 Enum 금지) | 명세서 §12 |
| 5 | 날짜/시간은 ISO-8601 (`2026-08-07T21:10:00+09:00`) | 명세서 §10 |
| 6 | 목록이 비어 있으면 `[]`, 단일 객체 미존재 시에만 `result: null` | 명세서 §15 — `undefined` 없음 |
| 7 | 목업 데이터끼리 FK 정합성을 유지한다 | 제품이 참조하는 성분 ID는 반드시 성분 목록에 존재 |
| 8 | 리포트 그래프 점수 = 피부 기록 점수 (교차 화면 정합) | S-08 결과와 S-09 그래프가 같은 값을 보여야 함 |

## 2. 공통 응답 봉투

모든 API 응답은 아래 4개 필드를 가진다. 화면 코드는 `result`를 바로 쓰지 말고 반드시 `isSuccess`를 먼저 확인한다.

### 성공

```json
{
  "isSuccess": true,
  "code": "COMMON_SUCCESS",
  "message": "Success.",
  "result": { }
}
```

- 생성(POST) 성공 시 `code`는 `COMMON_CREATED`

### 실패

```json
{
  "isSuccess": false,
  "code": "PRODUCT_NOT_FOUND",
  "message": "Product not found.",
  "result": null
}
```

### Validation 실패 (유일한 예외 — result에 errors가 담김)

```json
{
  "isSuccess": false,
  "code": "COMMON_VALIDATION_FAILED",
  "message": "Validation failed.",
  "result": {
    "errors": [
      { "field": "nickname", "reason": "Nickname length must be between 2 and 10." }
    ]
  }
}
```

## 3. Enum 정의 (목업·화면·백엔드 공통)

| Enum | 값 | 사용처 |
| --- | --- | --- |
| provider | `KAKAO` `GOOGLE` `EMAIL` | 로그인, 마이페이지 |
| gender | `FEMALE` `MALE` `NOT_SELECTED` | 온보딩, 프로필 |
| skinType | `OILY` `DRY` `SENSITIVE` `UNKNOWN` | 온보딩 (UNKNOWN은 단독 선택만 가능) |
| timePeriod | `MORNING` `NIGHT` | 루틴, 기록 |
| homeType | `DAY` `NIGHT` | GET /home |
| weather | `SUNNY` `CLOUDY` `RAINY` `SNOWY` | 홈 환경 카드 ※값 목록 백엔드 확정 필요 |

| reactionType | `SUITABLE` `CAUTION` `INSUFFICIENT` | 성분 프로파일 |
| riskLevel | `LOW` `MEDIUM` `HIGH` `INSUFFICIENT` | 구매 전 확인 |

## 4. 엔드포인트별 result 구조

### 4-1. AUTH-01 · POST /auth/login (S-00)

| 필드 | 타입 | 비고 |
| --- | --- | --- |
| accessToken | string |  |
| refreshToken | string |  |
| isNewUser | boolean | true면 온보딩 진입 |
| onboardingCompleted | boolean | 라우팅 분기 기준 |

### 4-2. HOME-01 · GET /home (S-01, S-02) — BFF

```json
{
  "homeType": "DAY",
  "environment": {
    "location": "서울특별시",
    "weather": "SUNNY",
    "temperature": 30,
    "humidity": 61,
    "uvIndex": 7
  },
  "todayRecord": {
    "productCompleted": false,
    "skinCompleted": true
  },
  "routine": {
    "routineId": 1,
    "title": "Morning Routine",
    "productCount": 3
  }
}
```

- `homeType`은 사용자의 wakeTime/sleepTime 기준으로 백엔드가 계산 (수동 토글 존재 시 프론트에서 재평가 생략 — 확정 결정사항)
- 밤 화면의 `uvIndex`는 당일 최고 UV 기준 (ERD §8)
- **루틴 없는 신규 사용자는 `routine: null`로 가정** → 백엔드 확인 필요 항목 (§7-4)

### 4-3. PRODUCT-01 · GET /product-records/home (S-04) — BFF

| 필드 | 타입 | 비고 |
| --- | --- | --- |
| routine | object 또는 null | `{routineId, title, productCount}` |
| savedProducts | array | `{productId, name, brand}` 목록, 없으면 `[]` |
| todayRecorded | boolean | 오늘 기록 완료 여부 |

### 4-4. PRODUCT-02 · GET /products?keyword= (S-06 검색)

result가 **배열 그 자체**다 (객체로 감싸지 않음).

```json

  { "productId": 11, "name": "라운드랩 자작나무 수분 토너", "brand": "Round Lab", "saved": true }
]
```

- keyword 1~50자 위반 시 422, 결과 없으면 `[]`, 최대 20건

### 4-5. PRODUCT-03 · GET /products/{productId} (S-06 상세)

| 필드 | 타입 | 비고 |
| --- | --- | --- |
| productId | number |  |
| name | string |  |
| brand | string |  |
| category | string | `TONER` 등 — 값 목록 백엔드 확정 필요 |
| saved | boolean |  |
| ingredientCount | number | ingredients 배열 길이와 일치해야 함 |

### 4-6. PRODUCT-04 · POST /products/scan (S-05, multipart)

result: `{ "productId": 15 }` — 이후 PRODUCT-03을 이어서 호출하는 흐름

### 4-7. PRODUCT-05 · POST /product-records (핵심 API)

- 요청: `{ "productIds": [11, 15, 18] }` (최소 1개, 최대 30개)
- 응답: `{ "recordId": 31 }`, code는 `COMMON_CREATED`
- 오늘 이미 기록한 제품 → `PRODUCT_ALREADY_RECORDED_TODAY` (409)

### 4-8. SKIN-01 · POST /skin-records (S-07, multipart)

- 요청: image 파일 1개 (jpg/jpeg/png, 10MB 이하)
- 응답: `{ "skinRecordId": 31 }`
- **분석 완료까지 수 초 소요 → 목업에서 2.5초 지연을 걸어 로딩 UI를 미리 검증**

### 4-9. SKIN-02 · GET /skin-records/today (S-08)

```json
{
  "skinRecordId": 31,
  "capturedAt": "2026-08-07T21:10:00+09:00",
  "scores":  { "trouble": 81, "redness": 66, "moisture": 74 },
  "changes": { "trouble": -4, "redness": 3, "moisture": 5 }
}
```

- `changes`는 이전 기록 대비 변화량, **음수 가능**
- SKIN-03(특정 기록 조회)은 동일 구조에서 **`changes`만 없음** — 주의

### 4-10. CHECK-01 · GET /checks/home (S-10)

| 필드 | 타입 | 비고 |
| --- | --- | --- |
| profileCompletion | number | 0~100 |
| recentChecks | array | `{checkId, productName, riskLevel}` |

### 4-11. CHECK-02 · POST /checks (S-10 → S-11)

- 요청: `{ "productId": 11 }`

```json
{
  "checkId": 13,
  "riskLevel": "LOW",
  "matchedIngredients": ["판테놀", "세라마이드엔피"],
  "cautionIngredients": [],
  "unknownIngredients": ["히알루론산"]
}
```

- ⚠️ 성분이 **문자열 배열**임 — CHECK-03과 타입이 다름 (§7-1)
- 프로파일 데이터 부족 시 `CHECK_PROFILE_NOT_READY` (409)

### 4-12. CHECK-03 · GET /checks/{checkId} (S-11)

```json
{
  "riskLevel": "LOW",
  "matchedIngredients": [ { "ingredientId": 2, "name": "판테놀" } ],
  "cautionIngredients": [ { "ingredientId": 7, "name": "향료" } ]
}
```

- ⚠️ 여기서는 성분이 **객체 배열**이고, `unknownIngredients`가 없음 (§7-1, §7-3)

### 4-13. REPORT-01 · GET /reports?period=7 (S-09)

```json
{
  "period": 7,
  "graph": [
    { "date": "2026-08-01", "score": 73 },
    { "date": "2026-08-07", "score": 81 }
  ],
  "todayScore": 81,
  "change": 2,
  "insights": [

```

- 데이터 부족 시 `REPORT_DATA_INSUFFICIENT` (409) → 위치별로 팝업/잠금 카드 분기 (확정 결정사항)

## 5. 목업 원천 데이터 세트

목업 함수가 조합해서 쓰는 원천 데이터. **아래 데이터끼리는 FK가 전부 맞물려 있어야 한다.**

### 5-1. 성분 (12종)

| id | 한글명 | 기능 | 프로파일 |
| --- | --- | --- | --- |
| 1 | 정제수 | 용제 | — |
| 2 | 판테놀 | 진정 | SUITABLE (지연 2일) |
| 3 | 세라마이드엔피 | 보습 | SUITABLE (지연 1일) |
| 4 | 나이아신아마이드 | 미백 | — |
| 5 | 글리세린 | 보습 | — |
| 6 | 히알루론산 | 보습 | — |
| 7 | 향료 | 착향제 | CAUTION (지연 1일) |
| 8 | 에탄올 | 용제 | CAUTION (지연 1일) |
| 9 | 살리실릭애씨드 | 각질 | INSUFFICIENT |
| 10 | 마데카소사이드 | 진정 | — |
| 11 | 티타늄디옥사이드 | 자외선차단 | — |
| 12 | 레티놀 | 주름개선 | INSUFFICIENT |
- INSUFFICIENT는 "데이터 부족 시 임의 분류하지 않음" 규칙(ERD §9) 검증용으로 반드시 포함

### 5-2. 제품 (6종)

| id | 제품명 | 카테고리 | 성분 id (표시 순서) | 저장 여부 |
| --- | --- | --- | --- | --- |
| 11 | 라운드랩 자작나무 수분 토너 | TONER | 1, 5, 6, 2, 3 | O |
| 15 | 토리든 다이브인 세럼 | SERUM | 1, 6, 2, 10, 5 | O |
| 18 | 일리윤 세라마이드 아토 크림 | CREAM | 1, 5, 3, 2 | O |
| 21 | 조선미녀 맑은쌀 선크림 | SUNSCREEN | 1, 11, 5, 4 | O |
| 24 | 섬바이미 AHA BHA PHA 토너 | TONER | 1, 8, 9, 7, 4 | X |
| 27 | 코스알엑스 레티놀 0.1 크림 | CREAM | 1, 5, 12, 3 | X |
- 제품 24는 주의 성분(향료·에탄올) 2개 포함 → 구매 전 확인 **HIGH** 시연용
- 제품 11은 맞음 성분 위주 → **LOW** 시연용

### 5-3. 사용자·루틴

| 항목 | 값 |
| --- | --- |
| 닉네임 / 성별 / 출생연도 | 윤진 / FEMALE / 2003 |
| 수면 | 취침 23:00 / 기상 07:00 (낮·밤 판정 기준) |
| 피부 타입 | DRY + SENSITIVE (복수 선택 검증용) |
| 지역 | 서울특별시 |
| 모닝 루틴 (id 1) | 제품 11 → 15 → 21 |
| 나이트 루틴 (id 2) | 제품 11 → 15 → 18 |
- 루틴에 넣는 제품은 **반드시 저장 제품(5-2의 O)이어야 함** — RoutineProduct가 UserProduct를 FK로 참조하기 때문

### 5-4. 피부 기록 (최근 7일, 밤 기록)

| id | 날짜 | 종합 | trouble | redness | moisture |
| --- | --- | --- | --- | --- | --- |
| 25 | 08-01 | 73 | 70 | 72 | 77 |
| 26 | 08-02 | 76 | 74 | 71 | 83 |
| 27 | 08-03 | 74 | 72 | 69 | 81 |
| 28 | 08-04 | 78 | 79 | 70 | 85 |
| 29 | 08-05 | 76 | 77 | 68 | 83 |
| 30 | 08-06 | 79 | 82 | 70 | 85 |
| 31 | 08-07 | 81 | 81 | 66 | 74 |
- **이 표 하나가 세 화면의 단일 소스**: S-08 오늘 결과(id 31), S-08 변화량(31−30), S-09 그래프(7일 전체)
- 하루당 (날짜, 시간대) 조합 1개 — ERD의 UNIQUE 제약 준수
- 점수가 단조 증가하지 않게 구성 (하락 구간 08-03, 08-05 포함) → 그래프·변화량 음수 UI 검증

### 5-5. 오늘 환경

| 항목 | 값 |
| --- | --- |
| 날씨 / 기온 / 습도 | SUNNY / 30℃ / 61% |
| 현재 UV / 당일 최고 UV | 7 / 9 |
- 낮 화면은 현재 UV(7), 밤 화면은 최고 UV(9)를 표시 — 두 값을 다르게 두어 낮/밤 분기 검증

## 7. ⚠️ 백엔드 확인 요청 (연동 전 필수 — 명세서 불일치)

| # | 항목 | 내용 | 프론트 임시 처리 |
| --- | --- | --- | --- |
| 1 | CHECK-02 vs CHECK-03 성분 타입 | POST /checks는 `string[]`, GET /checks/{id}는 `{ingredientId, name}[]`로 서로 다름 | 두 타입을 분리해 정의. **객체 배열로 통일 요청** (id가 있어야 성분 상세 이동 가능) |
| 2 | GET /users/me 이중 정의 | AUTH-04는 인증 확인용 최소 응답, MY-01은 마이페이지 대시보드 — 같은 URI에 응답 2개 | 용도별로 분리 정의. URI 분리 또는 통합 확정 요청 |
| 3 | CHECK-03에 unknownIngredients 없음 | CHECK-02에는 있는 필드가 상세 조회에는 없음 | 누락으로 추정, 추가 여부 확인 |
| 4 | 루틴 없는 신규 사용자의 GET /home | 명세에 예시 없음 | `routine: null` 가정 (명세 §15 근거) |
| 5 | weather / category Enum 값 목록 | 명세에 전체 값 미정의 | 목업 값으로 임시 사용, 목록 확정 요청 |
| 6 | 피부 지표 개수 | 명세 전체에서 trouble/redness/moisture **3개 고정** | S-20 육각 레이더 차트는 현 스펙과 불일치 — AI 지표 수 확답의 근거 자료로 사용 |

## 8. 백엔드 교체 전략

목업을 별도 API 레이어(함수)로 감싸 두고 화면은 그 함수만 호출한다. 백엔드 완성 시 **함수 내부만 실제 HTTP 호출로 교체**하면 화면 코드는 변경 없음. 교체 시점 체크리스트:

- [ ]  응답 봉투 4필드 확인 (`isSuccess`가 boolean인지, 문자열 "true"가 아닌지)
- [ ]  ID가 number로 오는지 (Long → 문자열 직렬화 여부)
- [ ]  날짜에 `+09:00` 오프셋이 포함되는지
- [ ]  빈 목록이 `[]`인지 (`null` 아님)
- [ ]  §7의 불일치 6건 확정 반영
- [ ]  401 시 AUTH-02 재발급 인터셉터 동작
